# M16 A start that explains itself: coverage

The M16 run: `python acceptance/run.py --repeat 3 --check US-085 --check US-086 --check US-087 --check DEF-29 --check "ENV-01 CFG-01"`, selecting the 11 M16 checks, from 18:15Z to 18:32Z on 2026-11-21, at the checks' commit `2034d04`. The owner cut this round's acceptance to one repeat while it ran, so the run was stopped by the harness's process id after its second repeat, at a point where no game process ran (the third repeat had not started a game); 22 of 22 passed, each check 2 of 2, so each passed its one required run. The framework was the install in `target\shakedown\` of the main checkout; `shakedown version` prints `0.1.6`. Steam ran for every start and no start was lost to `Error 20 reading file`.

Before it, two runs at the first commit of the checks, `5604e07`: a trial of one repeat on 2026-11-20 passed 11 of 11; a `--repeat 3` run on 2026-11-21 just after the machine restarted passed every check in its second and third repeats except one, for two reasons, neither a finding:

- `US-087`'s first check failed 3 of 3 with `start_timeout = 60`: on the cold machine `p1` had not connected either at 60 s, so both clients were `launched` and the reason named `p1`, which `SES-04` allows (it names one machine that got least far). A mistake of the check: its setup `hung` takes `start_timeout = 150`, room for `p1` to be ready, and the check then passed every run.
- In its first repeat a singleplayer client of the US-086 part never connected and its start failed at the start ceiling of 180 s, `p1` still `launched`: the hang of `DEF-28` (open, no connect ceiling since `SPK-20` failed). It did not repeat in that check, in that run or the next.

## How the checks drive it

The harness's project `m16`, in the work folder, holds one check, `US-086-version`, and a `shakedown.toml` with `base_port = 2602`, the mod `fixture` (`@skd_fixture`, patch `skdfx_main`, with a `version` only where a part writes one) and the mod `gone`, whose folder does not exist; its setups are `sp`, `ded` (two clients), `hung` (`ded` with `start_timeout = 150`) and `gap` (one client, `fixture` and `gone`). Per repeat, with no session before each part:

- **US-085 1 and 3.** With UDP port 2604 bound by a socket of the harness, `session start --setup gap` exits 4 in about 1.4 s with one message: `missing: the folder <work>\m16-no-such-mod of mod gone; free ports 2602 to 2606 for the server; 2604 held by another program (stop it, or set base_port in shakedown.toml)`. No game process is seen while it runs (processes listed every second), `status` shows no session, and `session_start` of `gap` through `shakedown mcp` returns `precondition-failed` with the same text. With Steam logged in the message names no Steam gap.
- **US-085 2.** The harness writes a project into an ISO image (the system's IMAPI2 file system image) and mounts it with `Mount-DiskImage`, a drive with 0 bytes free. `session start --setup sp` from it exits 4: `2 GB free on drive D:, which holds D:\; it has 0.00 GB free`, and `session_start` returns the same text. The image is dismounted after.
- **ENV-01, CFG-01.** A mod naming `version` without `patch` makes `session start` exit 3 naming `version` and its line.
- **US-086.** In singleplayer, a start with no `version` key is ready, the check passes and the result file records `fixture` at `0.0.6` on `p1`; `session stop` writes `session.json` with `reason: null` (`DEF-29` 3). With `version = "9.9.9"` the start exits 4, `failed`: `a mod was loaded in another version than the project names: mod fixture on p1 is version 0.0.6, and shakedown.toml wants version 9.9.9`, no game process runs 10 s after it, `status` shows it `failed` with that reason, `session stop` clears it and `session.json` holds the same reason. With `version = "0.0.6"` the start is ready and the check passes. On `ded` with `version = "9.9.9"` the start launches its three machines and fails naming `fixture on server`, the version found and the one wanted, with every process stopped.
- **US-087, DEF-29 2.** `session start --setup hung`, with `p2`'s process suspended by its id as soon as `status` lists it (about 39 s into the start, `launched`), exits 4 at 152.5 s: `the session was not ready within the start ceiling of 150 s: p2 was launched ... p2 wrote no RPT line`, `reason.machine` `p2`, `rpt_tail` empty, and no process of the start, the suspended `p2` included, runs 10 s after it. `status` shows it `failed` with the same reason, `session stop` exits 0 and clears it, and `session.json` holds `state: failed` and the printed reason before and after the stop.
- **DEF-29 1.** `session start --setup ded`, with `p2`'s process ended by its id once its RPT holds 25 lines, exits 4: `p2 exited with code 1 before it was ready; it was launched`, and `session.json` holds `state: failed` and the same message, machine and `rpt_tail`, with no Steam ID, before and after `session stop`.

`DEF-29`'s criteria hold: 1 and 2 by the checks above, 3 by the `reason: null` of a session stopped from `ready` and by the earlier check of `US-035` (below), whose `session.json` says `stopped runner-died`; 4 by `docs/sessions-and-the-runner.md` and `docs/starting-and-failed-starts.md`, which say `session.json` keeps the reason of a failed start, and by `SES-10`, which states it for the reason `SES-04` gives.

- **US-085 1, Steam logged out.** The harness does not log Steam out, and the round may not; Steam ran logged in for every start. The owner's look: with Steam running and logged out, a start of `gap` with port 2604 held names all three gaps.
- **US-088.** Code sent to `p2` could not take it out of its mission without a rendered client window. On a ready dedicated session with two clients, `shakedown exec` on `p2` opened `RscDisplayMPInterrupt` over display 46 (its button 104 read `ABORT`, enabled) and `ctrlActivate`d it: for 70 s after, `p2` stayed in its mission with `getClientStateNumber` 10, and `status` kept every machine `ready`. What the round did see is that the guard does not fire on the session's own server: every dedicated start of M16 and of the earlier checks below came up `ready`.
