# M11 Late joiners: coverage

The last run: `python acceptance/run.py --repeat 3` with `--check` values selecting the 23 M11 checks, from 16:01Z to 16:17Z on 2026-11-15. The framework was the install in `target\shakedown\` (`shakedown 0.1.1`, built after the M11 build `d372461`); main was at `15df612`, and the commit that landed on main during the round touched only `coordinator/playbook.md`. Steam ran for every start, and no start was lost to `Error 20 reading file`. 67 of 67 passed: the `late` key check once, and each of the 22 others 3 of 3.

## How the checks drive it

Each repeat starts two sessions of its own, with no session running before, in the project `m11` the harness writes: `ded`, a dedicated server with `clients = 2`, `late = 1` and `headless = 1`, and `sp`, singleplayer, each loading `@skd_fixture` alone. In the `ded` session, while `status --json` is read four times a second in a thread of its own:

1. `US-066-join-late`, then `after`: a crate with a public variable on the server, `["p3"] call skd_fnc_join`, and `skd_fnc_expectAgree` over `server`, `p1`, `p2` and `p3` on its position and variable. `after` asserts `skd_fnc_machines` is `server`, `p1`, `p2`, `hc1` and every client's player alive.
2. The same check through `run_start`, `run_status` with `wait_s` 45 and `run_result` over the MCP server.
3. `US-067-leave-rejoin`, then `after`: `["p2"] call skd_fnc_leave`, the fixture's `skdfx_disconnected` read with `skd_fnc_expectOn`, then a wait for a server variable the harness sets with `shakedown exec` once `status` shows no `p2` and `p2`'s process has ended, then `["p2"] call skd_fnc_join` and `skd_fnc_player` for `p2`.
4. `US-067-leave-only`, then `after`.
5. `US-068-join-hangs` (`["p3", 30] call skd_fnc_join`), then `after`, twice: once with `p3`'s process suspended by its id with `NtSuspendProcess`, once ended with `taskkill /F` by its id, each as soon as `status` listed `p3` and its RPT held 5 lines.
6. The five wrong calls of `US-069`, each followed by `after`.

In the `sp` session, `US-069-sp-leave` and `after-sp`. A separate project with `late = 9`, and one with `late = "one"`, are given to `session start`.

## Decisions of the test developer

- **One `hc1` in the dedicated setup.** `US-069` needs a headless client to refuse, so the setup adds `headless = 1` to the `clients = 2` and `late = 1` the stories name. The machines a check starts with are therefore `server`, `p1`, `p2` and `hc1`.
- **"`status` shows no `p2`"** is seen while the check that left `p2` waits on a server variable. The harness sets that variable with `shakedown exec` only once `status` lists no `p2` and its process has ended, so the check cannot join `p2` again before the harness has seen it gone.
- **"Ready" during a run** is read as not broken: `status` gives the session `running` while a run executes, and `ready` once it ends.
- **"Right after its launch"** is the first `status` that lists `p3` with a process id and an RPT of at least 5 lines. That way the evidence has RPT lines to hold. The lines are judged by finding at least one of them in `p3`'s RPT, since lines are redacted.
- **Exit code**: the harness ends `p3` with `taskkill /F`, which leaves exit code 1, and the check looks for it in the message.
