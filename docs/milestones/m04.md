# M4 Agent tools: report

## Decisions written into the spec

- `INS-02`, the session status machine and both contracts: `status` keeps a failed start with its reason until the next start or `session stop`, which clears it and exits 0 (`DEF-10`). The kept session keeps its machines, each `stopped`, as `INS-04` lists a machine from its launch in every state.
- `US-064`: a fourth criterion, the failed start (`DEF-12`).
- The MCP contract: a result over 20,000 characters is `{"result_path": path}`, which every `outputSchema` allows; `exec`'s `ceiling` defaults to 10 and its errors outside a check have `check_id` `null`; `wait_until` and `expect` take one machine; operands that do not fit `expect`'s operator are `bad-arguments`; `errors` needs a session; `inspect`'s radius defaults to 50.
- The tech stack: `rmcp` 3.9.0; the tool schemas are JSON in `tools.json` and take their shared shapes from `result.schema.json`, and `schemars` comes only through `rmcp`.

## The demo

On the Windows test machine, with Steam running and logged in, no game running, the owner connected, and the install folder on `PATH`:

```
python tools/install.py
set PATH=%CD%\target\shakedown;%PATH%
cd e2e\grappling-hook
claude
```

Claude Code asks to trust the project's `shakedown` server. Then ask the agent to start a singleplayer session with setup `sp`, run the M1 check through `run_start` and `run_status`, read `run_result`, and ask `inspect` where `p1` stands. The agent calls `session_start`, `run_start`, `run_status` until the run is `finished`, `run_result`, and `inspect` with `machine` `p1`, whose `player.position` is where `p1` stands. Stop the session with the agent's `session_stop`, or `shakedown session stop`.

On 2026-11-09 the owner ran it in a fresh Claude Code session started in `e2e/grappling-hook`, with `target\shakedown` on that window's `PATH`. With only the shakedown tools, the agent read `guide`, started a singleplayer session with setup `sp`, ran `US-009-let-go-key` through `run_start` and `run_status`, read a pass from `run_result`, asked `inspect` where `p1` stands, and stopped the session. No shakedown command was typed by a person.

The runs are in [the M4 coverage](../../acceptance/coverage/m04.md).

## Left out

- A cancelled `session_start` or `reset` goes on in the runner; `docs/agent-tools.md` says so (`DEF-13`).
- A run started with `run_start` is followed by the MCP server that started it; another server answers `run_status` and `run_result` only for runs that ended, from their result files. A session that outlives the Claude Code session is M5.
- A wait sees that its condition raised a script error by the count of errors on its machine during the evaluation, so an error that another script raises on the same machine in that frame also ends it.
- `exec` of a machine that does not answer gives the state `lost` and leaves the machine and the session as they are; `inspect` of a machine that stopped answering is M9.
- `errors` lists the running session's errors only, up to the last 1,000; a stopped session's are in its result files.
- `run_stop` (M8) and `reload` (M6).
- After a reset in which `RST-05` replaced a dead singleplayer `p1`, a later check failed `script-error` on `tsw_camtargetunit` errors on `p1`; the death camera may still run (`DEF-14`, no milestone yet).
- A start refused because Steam is not running still starts a runner, which stays up about 60 s (`DEF-15`, no milestone yet).
- An `exec` of code that does not compile lists its error twice (`DEF-16`, no milestone yet).
- With no project, a tool result over 20,000 characters goes to `shakedown-results` in the system temp folder, which no document names (`DEF-17`, no milestone yet).
