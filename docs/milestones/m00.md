# M0 Walking skeleton: report

## What it built

| Part | Where | What it does |
|---|---|---|
| The `shakedown` binary | `crates/shakedown/` | `list`, `run [<id>...] [--tag] [--setup]`, `session start --setup`, `session stop`, `version`, `--project`, `--json`, the exit codes of the contract; the runner (`shakedown runner`) started detached with no inherited handle, `runner.json` with its `skd_r_` token, an exit by itself 60 s after its last session and client, `runner.log`. |
| The session | `crates/shakedown/src/runner/session.rs`, `mission.rs`, `win.rs` | The singleplayer preconditions of `SES-03`, the session folder, mission and `autotest.cfg` of `INT-AR-04`, `p1` started with the options of `INT-AR-02` suspended in a job object with kill-on-close and resumed (`STP-01`), its environment of `SEC-02`, `ready` with a start ceiling and the RPT tail on failure, the versions of mods with a `patch` key, and the stop of `P-10`. |
| The run | `crates/shakedown/src/runner/run.rs`, `checks.rs` | The header of `API-01` read fresh for each execution, comments turned into spaces, `@setups` honoured, the `check` order with the runner ceiling of `OBS-03`, `invalid` / `machine-lost` when the lead does not answer, and `result.json` in `.shakedown/runs/<run id>/` with the `.gitignore` of `CFG-02`. |

| The gates | `.github/workflows/ci.yml` | The bundle check, `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` on Windows and Linux, and `hemtt check`. |

## Tests

- **Without the game**, run by `cargo test` and on GitHub Actions: 7 in `shakedown-protocol`, 4 in `shakedown-ext` (the bridge against a stand-in runner, including `SPK-03`'s hello), 27 in `shakedown` (project file, header, comments, selection, mission files, tokens, the job object and the environment of a started process, and three result files validated against `result.schema.json`).
- **With the game**, ignored by default and run on the test machine after `python tools/install.py`:
  - `cargo test -p shakedown --test e2e -- --ignored --nocapture --test-threads=1`: `us_037_us_038_checks_in_one_session` (every acceptance criterion of `US-037` and `US-038`, each result file validated against the schema) and `run_04_the_demo_starts_and_stops_its_own_session`, which drives the demo once.
  - `cargo test -p shakedown --test demo_repeat -- --ignored --nocapture`: `p_01_run_04_the_demo_five_times_leaves_nothing_running` (exit criterion 2). It takes about nine minutes and runs only by name, when the milestone closes.
  - `cargo test -p shakedown --test spikes -- --ignored --nocapture`: `SPK-01`, `SPK-02` and `SPK-03` for `p1`, and the cost of `compile` by size.

## Spikes

All three passed for singleplayer `p1`; the measurements are in [research/22-spikes-singleplayer-channel.md](../../research/22-spikes-singleplayer-channel.md). `SPK-02` found that the channel holds the 100 ms frame limit at a megabyte, and that the engine's `compile` of a long string literal grows with the square of its length; `NFR-PF-05` and the check API contract say so.

## Decisions written into the spec

- `INT-AR-03`: `fetch` returns the part as unquoted text with a `1` or `0` prefix for last or more, so a part of JSON full of quotes still fits the 10240-byte result; `send` also queues while the connection is being made.
- `P-01`, `P-02`, `STP-01`: the runner creates one job object per session, at the session's start, instead of one for its own life.
- `P-02` steps 7 and 8: `ready` carries no mod versions; the runner reads them with an `exec` order once the machine is ready.
- `SES-03` and `P-02` step 3: Steam is looked for in the current user's Windows session; the installed addon must hold its PBO and extension; the junction of `INT-AR-06` is for dedicated setups only, since a singleplayer client loads `@shakedown` from its installed path.
- The check API contract: comments may stand anywhere in a check and are turned into spaces, since `compile` takes none; long string literals compile slowly.
- The MCP contract: `list_checks` gives each check an `error`, the header mistake, so `list` shows a broken check instead of hiding it.
- `NFR-PF-05`: set from `SPK-02`.

The demo five times with the final build, `p_01_run_04_the_demo_five_times_leaves_nothing_running`, on 2026-11-05. The runner's exit is timed from the command's return, which follows the session's stop by under 0.5 s:

| Run | Exit code | Command took | `arma3_x64` left | Runner exited after |
|---|---|---|---|---|
| 1 | 0 | 40.4 s | no | 61.0 s |
| 2 | 0 | 41.0 s | no | 60.9 s |
| 3 | 0 | 41.9 s | no | 60.9 s |
| 4 | 0 | 40.0 s | no | 60.8 s |
| 5 | 0 | 39.2 s | no | 60.9 s |

An earlier build, without the runner's refusal of a client during its exit, ran the demo ten times in a row with the same result: exit 0 in 39.6 to 55.9 s, no game process left, the runner gone 60.3 to 61.9 s after each run.

## Left out

As the milestone says: dedicated sessions, the reset, every check API function not named, script errors in the result, logs, `status` and the MCP server. Also left out, each for the milestone whose story needs it:

- The run record and the recovery of `P-12` (M5), the process check of `SEC-03` through the TCP table and the audit of `SEC-04` (M5); a refused connection is logged without the other end's process id.
- The client's check of the runner's process start time against `runner.json` (`P-01` step 1, `US-060`, M5).
- `run stop`, Ctrl+C and the run ceiling (M8); a heartbeat and the clock watch (M9); a crash noticed by its process handle during a check (M9): in M0 a lost connection or the runner ceiling ends the check `invalid` / `machine-lost`.
- `skd_fnc_on` to a machine other than the lead, and the `DM-14` decoding of arguments (M2).
- The ACL of `runner.json`: it lives in the user's local application data folder, which only the user can read, and is written with no ACL of its own.
