# M5 A session that outlives its client: report

M5 is complete and released as `0.0.6`. Every exit criterion is met.

## What it built

| Part | Where | What it does |
|---|---|---|
| The detached start | `crates/shakedown/src/win.rs`, `client.rs`, `runner/mod.rs` | `SES-08`, `INT-WIN-02`: the client starts `shakedown runner` as a relay with `CREATE_BREAKAWAY_FROM_JOB` and `DETACHED_PROCESS`, marked by `SHAKEDOWN_RUNNER_RELAY=1`; the relay starts the runner the same way and exits. When a job forbids breakaway, the client or the relay starts the runner through WMI's `Win32_Process.Create`, with `DETACHED_PROCESS` and `CREATE_NEW_PROCESS_GROUP`, so it has no console. The runner ignores Ctrl+C and Ctrl+Break and writes every console event, every panic and the way it was started to `runner.log`. |
| The run record and recovery | `runner/record.rs`, `runner/session.rs` | `STP-03`, `P-12`: `record.json` lists each session, each game process and the mission copy before the next step; every runner start clears what it lists and writes `stopped` with reason `runner-died` into the dead session's `session.json`. |
| A runner that cannot be reached | `client.rs`, `ops.rs`, the MCP tools | `P-01`, `INS-02`, `INS-04`, `AGT-02`: a client checks `runner.json`'s process id and start time; a runner that does not answer or answers another version is refused with `runner-unreachable` and exit 4, naming its process id, both versions where they differ, and that ending it ends its session; `status` shows the runner `unreachable` with its `runner_pid`. No second runner starts. |
| Local control | `runner/mod.rs`, `win.rs` | `SEC-01`, `SEC-03`: an extension is let in only from the process the runner started for that machine, read from the system's TCP table; every refusal goes to `runner.log` in the contract's form. `SEC-02`, `INT-WIN-03`: `runner.json` is written under a temporary name with a protected access list that grants the current user alone, then renamed into place (`m05-1`). |
| The audit | `runner/control.rs`, `runner/run.rs` | `SEC-04`: every `exec` from the command line and MCP, each check's body and each piece of code a check sends to another machine goes to `audit.jsonl` in the session folder, redacted. |
| The docs | `docs/sessions-and-the-runner.md`, `docs/install.md`, `docs/agent-tools.md` | What happens to a session when its client or its runner ends, how to end a runner that cannot be reached, and what the runner lets in. |

## The spike

`SPK-06` passed, under Claude Code 2.1.319 on the test machine ([the spike's research](../../research/26-spike-runner-detach.md)). Claude Code runs a stdio server in a kill-on-close job that allows silent breakaway and ends it by closing its input. The relay with WMI as its fallback keeps the runner alive in all three ways a host can end its server: a kill-on-close job that forbids breakaway, one that allows it, and `taskkill /T /F` of the tree. The scheduled-task fallback is not needed, and `INT-WIN-02` says what the spike found. The spike also found that a runner started by WMI got a hidden console of its own, and a console event ended it with `0xC000013A`; WMI starts it with no console.

## Decisions written into the spec

- `INT-WIN-02`: the relay with `SHAKEDOWN_RUNNER_RELAY=1`, WMI as the fallback of client and relay, and a start with no console.
- `P-01` and the command line contract: `runner.json`'s `started_at` is the start time of the process `pid`; a file that names no live runner is deleted and a runner started.
- `STP-03`, `P-12`, `STP-04`: when the record is written, and `runner-died` in the dead session's `session.json`.
- `SEC-04`: the sources `cli`, `mcp` and the check id, and which code of a check goes into the audit.
- `US-035` criterion 2: `status` after the runner died shows it `not-running` and starts none; the next `session start` starts one.

## The demo

On the Windows test machine, with Steam running and logged in, no game running, the owner connected, and the install folder on `PATH`:

```
python tools/install.py
set PATH=%CD%\target\shakedown;%PATH%
cd e2e\grappling-hook
claude
```

Ask the agent to start a dedicated session with setup `dedicated` and end the Claude Code session. Start a new one with `claude` in the same folder and ask it for the session's status, then to run the M2 check `US-009-dedicated-freed-rope` against it. Then end the runner with `taskkill /PID <runner_pid> /F`, the id `shakedown status` gives, and check that no `arma3_x64` or `arma3server_x64` process is left within 10 s.

On 2026-11-09 the owner ran it in a fresh interactive Claude Code session started in `e2e/grappling-hook`. A first Claude Code session started a dedicated session through MCP and ended. A second found the same session `ready` and ran `US-009-dedicated-freed-rope.sqf` against it, which passed. The runner was then killed with `taskkill /PID <id> /F`; no game process was left within 10 s, and `status` showed the runner `not-running`. The owner said everything went according to spec.

## Acceptance

The test developer's rounds wrote one finding, for the developer: `m05-1`, `runner.json` inherited its folder's access list, which also let the Administrators group read the runner token, where `SEC-02` and `INT-WIN-03` promise the current user only. The developer answered it with a protected access list that grants the current user alone; the check passed 3 of 3 in its verify round, and the finding is verified. The M5 rounds ran every other M5 check 3 of 3 against the framework from `1d2d47a`, `US-007` among them under headless Claude Code. The last full run, at `fbf9b52` against the framework installed from `af74f05`, passed all 191 checks: M5 21 of 21 and M0 to M4 170 of 170. The runs are in [the M5 coverage](../../acceptance/coverage/m05.md).

## Left out

- `audit.jsonl` holds every `exec` and the code of a check, but not the condition of `wait` or `wait_until`, the value of `expect`, or the code `inspect` sends (`DEF-18`, no milestone yet).
- In one of 25 rounds a runner started by WMI wrote `runner.json` more than 10 s after its start, past the 10 s a client waits; it did not recur in 15 timed rounds (`DEF-19`, no milestone yet).
- A `runner.json` lost while its runner lives starts a second runner, whose recovery ends the first session's game (`DEF-01`, no milestone yet).
- The process that sent the console event to a WMI-started runner is not identified; the runner has no console, and logs any event it receives.
