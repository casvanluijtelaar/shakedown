# Functional requirements

Each requirement has an ID of the form `AREA-nn` and cites the PRD requirements (`CR-nn`) it serves. Requirements marked **must** are the first release (the MVP). Those marked **should** or **could** are held open by one entry and are specified when a milestone takes them up. The traceability table at the end maps every `CR-nn` to its requirements.

The exact names, arguments and outputs of the interfaces are in the contract: [contract/check-api.md](contract/check-api.md), [contract/cli.md](contract/cli.md), [contract/mcp-tools.md](contract/mcp-tools.md) and [contract/result-file.md](contract/result-file.md). Where a requirement and the contract disagree, the requirement wins and the contract is fixed.

## Project configuration

- **CFG-01** (must) A project is configured by one `shakedown.toml` file at its root, with the keys the CLI contract lists: the game folder, the tests folder that holds the checks, the server's base port, the slow step threshold (`TIM-01`), each mod (its folder, and for a watched mod its `source` folder and its game `prefix`), and the setups (mode, clients, headless clients, mods, world, spawn point, start ceiling). Every command reads it fresh. An unknown key, a missing required key or a wrong type is refused with the key's name and line (`CR-01`, `CR-41`).
- **CFG-02** (must) The framework writes nothing into the project except the `.shakedown/` folder, which it creates with a `.gitignore` that ignores everything in it, so session and run folders stay out of git (`CR-51`, `CR-24`; gap H8).

## Sessions

- **SES-01** (must) `session start --setup <name>` starts a session of the named setup: one singleplayer game, or a dedicated server with the setup's game clients and headless clients, all on the local machine. It returns when the session is `ready` (every machine answers in the session mission) or `failed` (`CR-01`).
- **SES-02** (must) At most one session runs on the machine. A second `session start` is refused, naming the running session's id and setup and the command that stops it (`CR-01`).
- **SES-03** (must) Before any process starts, the start checks that the game's `arma3_x64.exe` (and for a dedicated setup `arma3server_x64.exe`) exist in the configured game folder, that a process `steam.exe` runs in the current user's Windows session, that every mod folder of the setup exists, that the framework's installed addon holds its PBO and its extension, and, for a dedicated setup, that the five ports from the base port are free, read from the system's UDP table without binding them (`NFR-SC-01`). A failed check refuses the start and names exactly what is missing (`CR-01`, scenario "things go wrong" 4).
- **SES-04** (must) A start has a ceiling of 180 s from the first process launch to `ready`, settable per setup with `start_timeout`. At the ceiling, or when a process exits during the start, the session is `failed`, every process it started is stopped, and the reason names the machine that was not ready, its state and the last 20 lines of its RPT; at the ceiling it names the machine that got least far, one still `launched` before one `connected`, and lists every machine not `ready` with its state (`CR-01`, `CR-05`).
- **SES-05** (must) A `ready` session runs any number of runs, checks and `exec` calls without restarting a process. Only a reload at level `game-restart`, or a check with reset mode `mission`, restarts anything (`CR-01`).
- **SES-06** (must) A session belongs to the runner, not to the client that started it. When the command line exits or an AI agent's session ends and its MCP server stops, the game session keeps running and a new client finds it (`CR-01`, `CR-53`; gap H6).
- **SES-07** (must) `session stop` stops every process of the session and returns when none is left (`CR-05`).
- **SES-08** (must) The runner runs as its own detached process, outside the process tree and job object of any client, so that a client's host ending the client does not end the runner, whether the host closes a job object with kill-on-close that holds the client, with or without breakaway allowed, or terminates each process of the client's tree. Those are the two ways a host such as Claude Code ends a client, and a test reproduces either one around `shakedown mcp` (`CR-01`, `CR-05`; gap H6, `INT-CC-02`).
- **SES-09** (must) Every game process is started from the installed executables, with its own profile folder in the session folder, `-name=<machine>`, `-filePatching`, `-debug`, and every option of `INT-AR-02`. No game executable is copied (`CR-01`, `CR-03`, `CR-24`).
- **SES-10** (should) The reason of a failed start, as `SES-04` gives it, with its message, machine and RPT tail, redacted, is also written into the session folder's `session.json`, so it outlives the `failed` view of `status` and the runner (`CR-01`, `CR-06`; `DEF-29`). A start has no connect ceiling per machine besides the start ceiling: `SPK-20` measured a healthy client's launch to `connected` at up to 90 s, too near the start ceiling for one to help, so a hung client fails the start at the start ceiling (`DEF-28`; research `32-spike-connect-times.md`).

## Reset between checks

- **RST-01** (must) Before every check whose reset mode is `in-place`, the framework resets the session as process `P-06` says: runs the previous check's cleanups, deletes every entity created since the baseline (whatever created it), restores every player's unit (alive, position, direction, velocity, damage, loadout, animation state, out of any vehicle) and the date and weather. The next check sees the baseline state on every machine (`CR-02`; gap H2).
- **RST-02** (must) The baseline is captured at every mission start, so when the session first becomes `ready` and again after every mission restart and game restart: each machine's agent captures it once its player stands still on the ground in a settled animation state, not between two (a machine without a player once its mission time runs), before it reports `ready` (`P-02` step 7). It holds each player unit's position (ASL), direction, loadout and animation state and its group's behaviour, the date, and the overcast, fog and rain; the server's date and weather are the ones every machine is reset to (`CR-02`).
- **RST-03** (must) `reset` runs the reset on demand, outside a run. On a `broken` session it is refused with the reason the session broke and the two ways out, `reload`, which restarts the game of a broken session, and `session stop` (`CR-02`, `CR-27`).
- **RST-04** (must) A reset has a ceiling of 15 s. A reset that does not verify within it fails, names what did not match, and leaves the session `broken` (`CR-02`, `CR-31`).
- **RST-05** (must) A player who died is alive again before the reset ends: on a dedicated session the session mission's respawn brings the unit back at once, and the body it left, which the `EntityRespawned` mission event names on every machine, is deleted by the reset; in singleplayer, where the engine ends the mission when its player dies even with `respawn = 3`, the agent's `Killed` handler hands the player a new unit of the same class, in the same group, where the old one fell, with `selectPlayer`, before the engine ends the mission, and the reset deletes the body (`SPK-05`). A singleplayer session survives the player's death in every case (`CR-02`).
- **RST-06** (must) A check whose header says `@reset mission` gets a mission restart (level B of `P-08`) instead of a reset in place, for a check that changes state the framework cannot name, such as global variables or mod settings (`CR-02`; Q5).
- **RST-07** (must) The state a check left stays in the game until the next reset, so it can be inspected after the check ends (`CR-27`).

## Reload

- **RLD-01** (must) `reload [files...]` brings changed mod code into the running session at the level the change needs, as process `P-08` says. With no files given it finds the changed files itself by comparing the watched `source` folders with the snapshot taken at the last ready state. A `reload` or a `reset` asked while a run, a reload or a reset is in progress is refused, naming what is in progress: for a reload, its id and level; for a run, its id, its progress and `run stop`. A `reload` of a `broken` session applies level `game-restart`, whatever the files need, which brings every machine back as a new start (`CR-03`, `CR-05`).
- **RLD-02** (must) Each changed file is classified, and the highest level any file needs is applied (`CR-03`; conflict C1):

  | Change | Level | Reason given |
  |---|---|---|
  | A check file | none | Checks are read fresh for every execution (`RLD-04`). |
  | A file of the library folder | none | Every reload reads the library folder again and has every machine compile it (`API-06`). |
  | A `.sqf` file of a watched mod that the build already holds, whatever it defines (a `CfgFunctions` function, a CBA `PREP` function, code run at mission start) | `mission-restart` | The game is made to let go of the file by reading the framework's release files, and a mission restart compiles it again (`SPK-19`). |
  | A new or deleted file | `game-restart` | File patching finds only files that exist in the built PBO; the mod must be rebuilt before this reload, or by its `rebuild` during it. |
  | Any other file (`config.cpp`, `.hpp`, `.h`, `.inc`, `.ext`, string tables, models, textures, sounds) | `game-restart` | Config is read at game start; the others are not reloaded by file patching. |

  The game opens each loose mod file it reads shared for reading only, so while a game process holds it the file can be neither written nor replaced, and every machine keeps reading the content it holds, across a mission restart, until it lets go of the file (research `27-spikes-reload.md`). A game process lets go of the loose files it holds once it has read a few hundred MiB of other loose files through file patching (research `31-spike-reload-release.md`). So a reload of level `mission-restart` first has every machine read the framework's release files (`RLD-07`), checks that no game process holds a changed file, makes the change by the mod's `rebuild` (`RLD-06`) and restarts the mission (`P-08`). A file still held after two reads makes the reload a `game-restart`, and the file's entry in the result gives level `game-restart`, names the machine whose process holds it and says that the game did not let go of it (`US-082`). A mission restart compiles a CBA `PREP` function and code run at mission start from its file again, since the session mission turns CBA's function cache off (`INT-CBA-02`). The Functions Library compiles an addon's `CfgFunctions` function once per game process and copies it into each new mission, so after every mission restart that follows a reload of level `mission-restart`, until the next game restart, every machine recompiles each `CfgFunctions` function whose file the reload changed, with `BIS_fnc_recompile` (research `27-spikes-reload.md`). Reload has no level inside the mission (`DEF-32`).

- **RLD-03** (must) A reload reports the level applied, each file with its level and reason, the machines it reached, and the time from the reload order to every machine being ready on the new code (`CR-03`, `CR-42`).
- **RLD-04** (must) Checks are never reloaded by a command: the runner reads each check's source from disk at the start of every execution (`CR-03`).
- **RLD-05** (must) A check executed after a reload that had a machine recompile a `CfgFunctions` function, until the next game restart, records `reload: partial` in its result, because code that took the function by value at the mission start, such as an event handler a mod added in its `postInit` with the function as its code, keeps the old code on a machine whose process the mission restart kept (`CR-03`, `CR-31`).
- **RLD-06** (must) The framework does not build mods. A watched mod is loaded from a build of the developer's files that the game reads in their place, such as HEMTT's `hemtt build` output, so the files the developer edits are never the ones the game holds; its `source` is the developer's files. A mod's `rebuild` in the project file is the developer's own command that makes that build, such as `hemtt build`, or copies changed files into it: a `game-restart` reload runs it in the project folder after every game process has ended and before any starts, and a `mission-restart` reload runs it once no game process holds a changed file and before the mission restarts, in the order of the setup's mods, with a ceiling of 120 s. At level `mission-restart` the game processes still hold the mod's PBOs and every other file they read, so a rebuild there writes only the changed loose files, such as by copying them; a rebuild that writes a held file fails. A rebuild that fails or passes its ceiling still brings every machine back, on the files as they are, and fails the reload naming the mod. A reload of a new or deleted file of a mod with no `rebuild` states that a rebuild comes first (`CR-03`; PRD scope).
- **RLD-07** (must) The release files are one file of 8 MiB and 80 directory junctions to its folder, 640 MiB through 80 paths, in the folder `skd_release` of the game folder, which no PBO covers, so file patching finds them. The runner makes them when the first reload of level `mission-restart` needs them and keeps them. At that level every machine of the session reads all 80 paths with `loadFile`, all machines at once, within a ceiling of 60 s; the game keeps loose files by path, so each path counts as another file (`CR-03`; research `31-spike-reload-release.md`).

## Stopping and cleaning up

- **STP-01** (must) Every game process is started suspended, assigned to its session's job object, which the runner holds, with kill-on-close, and only then resumed, so it ends when the runner ends, however the runner ends (`CR-05`).
- **STP-02** (must) A run that passed, failed, was stopped by hand, or whose session broke leaves no process of its own running: a run that started its own session stops it, unless a check handed the session over to a manual tester (`MAN-01`); a run against an existing session leaves exactly that session's processes (`CR-05`, scenario "as planned" 5).
- **STP-03** (must) The runner keeps a run record at `%LOCALAPPDATA%\Shakedown\record.json` of every process (id and start time), every file and folder it created outside the project, and every session it started. It records a session and each file or folder before it creates them, and each process as soon as the process exists, before the session's next step, and clears what the record lists at its next start (`P-12`) (`CR-05`, scenario "things go wrong" 6).
- **STP-04** (must) After `session stop`, no `arma3_x64` or `arma3server_x64` process the session started runs, no port of the session is held, and no mission copy is left in the game's `MPMissions` folder (`CR-05`).

## Control: running code on a machine

- **CTL-01** (must) Code runs on a machine named by `DM-10`, or on each machine of a group named by `DM-12`, and its return value comes back as data, encoded by `DM-13`. For a group, the result is a map from machine name to value (`CR-10`, `CR-22`).
- **CTL-02** (must) Arguments travel as data and arrive as `_this`; they are never formatted into the code's text. The code does not see the caller's local variables (`CR-10`).
- **CTL-03** (must) Code always runs scheduled on the target machine (`spawn`), so it may wait, and every call has an in-game ceiling (default 10 s) and a runner ceiling (`OBS-03`) (`CR-10`, `CR-20`).
- **CTL-04** (must) A call to a machine the session does not have, or code that does not compile on the target, returns an error that names the machine or the engine's compile message, and inside a check ends it `fail` / `check-error` (`CR-10`, `CR-31`).
- **CTL-05** (must) A script error raised by code sent to a machine does not stop that code: it runs on and its value comes back with the error. Inside a check the error fails the check `fail` / `script-error` once the body ends (`ERR-03`), unless an `expectError` block matches it; through `exec` the answer lists the error beside the value, and the call succeeds (`CR-10`, `CR-23`).

## Scene

- **SCN-01** (must) The check API creates an object, a vehicle or a unit by class name at a position (ASL) and direction on the server, with vehicle randomisation off, and returns it (`CR-11`).
- **SCN-02** (must) The check API places a unit at a position (ASL) facing a direction: it sets the direction and then the position on the machine where the unit is local, and returns once the server sees the unit within 0.1 m and 3 degrees, polled to the wait ceiling (`CR-11`).
- **SCN-03** (must) The check API sets the date and the time of day, and the overcast, fog and rain, on the server, forces the weather change, and broadcasts them by setting the same on every other machine, then returns once every machine reports the same date and overcast (`CR-11`, `CR-22`).
- **SCN-04** (must) Anything a check creates by its own SQF on any machine is deleted by the next reset as well as what the API created, because each machine records every entity created (`CR-11`, `CR-02`).

## Acting through the mod's real path

- **ACT-01** (must) The check API makes the player of a named machine use an `addAction` action on a target object, found by its title (exact match after stripping structured-text tags). On the acting client it waits, to the wait ceiling, until the action exists, its condition holds with the documented variables, and the player is within its radius; then it fires it with `action ["User", target, id]`. The engine runs an action fired that way whatever its condition and radius (`SPK-10`), so this check of the framework's is the only one. When the ceiling passes it fails with the reason: no action of that title (with the titles that exist), the condition false, or the distance and the radius (`CR-12`).
- **ACT-02** (must) The check API presses a CBA keybind of a named mod and action on a named machine: it reads the bound key from `CBA_fnc_getKeybind` and calls the keybind's down code, its up code, or both in order, with `[display 46, DIK, shift, ctrl, alt]` (`CR-12`).
- **ACT-03** (must) A keybind step on a machine without CBA, or for a keybind that is not registered, ends the check `fail` / `check-error` with the keybinds registered for that mod, or, when it has none, the mods that have keybinds, both in lower case as CBA keeps them (`CR-12`, `CR-31`).
- **ACT-04** (should) Perform an ACE interaction menu action, on an object or on the acting player itself, by its path of action names, through ACE's own key-up code, `ace_interact_menu_fnc_keyUp`, on the acting client, pinned to the ACE version `INT-ACE-03` names (`CR-12`; gap H7, Q6; `SPK-21`, research `35-spikes-ace-and-keys.md`).
- **ACT-05** (should, dropped) Send real key input to one game client window without the foreground or the desktop's input. Dropped: spike `SPK-11` found that a key posted to the game's window reaches neither a key handler nor a CBA keybind, even with the game in the foreground, since the game reads the keyboard through DirectInput (research `35-spikes-ace-and-keys.md`); calling the keybind's code (`ACT-02`) covers every key path the checks need (`CR-15`; conflict C3).

## Observation

- **OBS-01** (must) Every wait polls its condition on the named machine, every frame, until it holds or its in-game ceiling passes on real time (`diag_tickTime`). The default ceiling is 10 s; every wait takes its own. A ceiling is a number of seconds above 0; any other value is a wrong argument (`DM-04`). A condition that raises a script error or returns anything but a Boolean ends the wait at that evaluation, with no retry: inside a check, `fail` / `script-error` when the machine caught a script error during it, otherwise `fail` / `check-error` naming the type it returned; through `wait`, an answer with `met` `false` and that cause (`CR-20`; gaps H4, H5, Q3).
- **OBS-02** (must) The check API has no fixed sleep. Every wait has a condition and a ceiling (`CR-20`).
- **OBS-03** (must) The runner holds its own wall-clock ceiling on every order and every check: the in-game ceiling plus a grace of 10 s. Reaching it with no answer makes the machine `lost` (`CR-20`, `CR-31`; gap H5).
- **OBS-04** (must) A wait or an assertion that ends at its ceiling reports the description, the ceiling, and the last observed value on each machine it polled (`CR-20`, scenario "things go wrong" 1).
- **OBS-05** (must) Every step record, script error and event carries the machine's name, the wall clock (`systemTimeUTC`), the machine's real time (`diag_tickTime`), its mission time (`time`) and its frame number (`diag_frameNo`) (`CR-23`, `CR-42`).
- **OBS-06** (must) The check API reads one value on several machines and asserts that each meets an expectation, or that every machine agrees with the first one named (within a tolerance for numbers and positions), polled to the ceiling. On failure it reports the value of each machine (`CR-22`).
- **OBS-07** (must) The check API has a wait that returns `true` or `false` at its ceiling instead of failing the check (`CR-20`).
- **EVT-01** (should) Record a named mod (CBA) or engine mission event on each machine with the clocks of `OBS-05`, and wait for one with a ceiling. Every handler a check's recording added is removed on every machine when the check ends, and the result file lists the events it recorded under the check (`CR-21`).

## Script errors

- **ERR-01** (must) Every machine's in-game agent catches each script error with the `ScriptError` mission event and sends it at once with its text, file, line, stack trace (each frame's file, line and scope, without its variables), the clocks of `OBS-05`, and the run id, check id and step path that were set on that machine when it fired (`P-05` step 6). The handler fires for every error the engine reports, in scheduled and unscheduled code, on every machine kind (`SPK-07`) (`CR-23`).
- **ERR-02** (must) The runner also reads each machine's lines for a check execution from its RPT and records every script error they show, by the pattern of `INT-AR-07` in [04-integrations.md](04-integrations.md), that no handler error of that machine with the same text and file accounts for, each handler error accounting for one. Such an error has `source` `rpt`, the wall-clock time of its RPT line to the second, and the step of the lead at that time (`P-05` step 7) (`CR-23`).
- **ERR-03** (must) A script error on any machine during a check's execution fails it (`DM-03`) unless it happened inside an `expectError` block whose pattern it matches, or a cause that came first in wall-clock time decided the outcome (`DM-06`). Errors during the reset before the body are listed with the execution but do not fail it (`DM-02`), and an error raised while compiling code the check sent is listed while the check ends `check-error` for it (`CR-23`, `CR-31`).
- **ERR-04** (must) `expectError` declares that an error containing a text (case-insensitive) is expected in a block of code. Matching errors on any machine until the check ends are marked expected; none matching by the end fails the check (`CR-23`).
- **ERR-05** (must) Script errors outside any check are kept with the session and returned by `errors` with their machine and time (`CR-23`, `CR-27`).

## Logs

- **LOG-01** (must) Each machine start writes its RPT and any crash dump to its own profile folder in the session folder, kept after the session stops (`CR-24`).
- **LOG-02** (must) Every log line the framework returns or stores outside the profile folders, every value and message in the result file and in what the command line and the tools return, and every profile folder's RPT once its session stops, has Steam IDs (17-digit numbers starting `7656119`) replaced by `<steamid>`, and the logged-in Steam account's account name and persona name (`INT-STM-04`), each matched as a whole word and case-sensitive, replaced by `<steamname>` (`CR-24`, `CR-51`; gap H8).
- **LOG-03** (must) `logs` returns a machine's log lines filtered by run, by check, by a regular expression and by count (the last N lines), redacted (`CR-24`).
- **LOG-04** (must) A run's folder holds each machine's log lines for the run's time span and for each check execution, redacted, one file per machine, and the in-game agent writes a marker line `[shakedown] <key> start <utc>` and `[shakedown] <key> end <utc>` at the run's start and end (the key is the run id) and at each check execution's start and end (the key is `<run id>#<n>`, `n` its place in the run), so those lines can be cut out. The engine writes a line to the RPT within about 0.5 s, and a reader beside the running game reads it (`SPK-13`) (`CR-24`, `CR-51`).

## Inspecting a running game

- **INS-01** (must) `inspect <machine>` returns, without stopping anything: the machine's state and start number, the mission and its start count, `time`, `diag_tickTime`, `diag_fps`, `diag_frameNo`, the run, check and step running, the step on the lead being the innermost step running in the check and on another machine the step the newest order still running there was sent from (a wait, a poll or code a step runs there), or none; the player unit (class, position ASL, direction, damage, alive, vehicle, animation); up to 50 objects within 50 m of the player or of a named object (class, net id, position, distance); up to 50 running scheduled scripts from `diag_activeSQFScripts`; and the last 10 script errors. The radius and the object are arguments. The order has an in-game ceiling of 10 s; a machine that does not answer within it plus the grace of `OBS-03` is `lost` as process `P-07` says, and `inspect` returns its machine with state `lost` and nothing else, instead of an error (`CR-27`).
- **INS-02** (must) `status` answers without a game: whether the runner runs and answers (`P-01`), the session's id, setup, state and each machine of `INS-04`, and the active run with its progress. A start that failed stays in `status`, with state `failed` and its reason, until the next `session start` or `session stop`; `session stop` then clears it and exits 0 (`CR-27`, `CR-53`).
- **INS-03** (must) `exec`, `inspect`, `logs` and `errors` work while a run is active and while the session is `broken` (`CR-27`).
- **INS-04** (must) `status`, and every session shape the command line and the tools return, list each machine from the moment its process is launched, and not before, in every session state including `starting` and `reloading`, with: its state and start number; its operating-system process id and process start time; its profile folder; its last answer time; its health flag of `HLT-02` and `HLT-01` (`null`, `frame`, `frame-rate`, `mission-time` or `answer-time`) and the time the flag was raised; its frame rate over the last 5 s and its answer time (`HLT-01`); and the clocks of `OBS-05` from its last heartbeat. `status` also gives the runner's process id. A person or an AI agent finds a machine's window, process and RPT from these, and an outside tool can suspend, end or dump a chosen machine's process by its id, which is how a stall, a crash and a crash dump are made on purpose (`CR-27`, `CR-53`, `CR-30`).

## Outcomes and health

- **OUT-01** (must) Every check execution ends `pass`, `fail` or `invalid` by the rules `DM-01` to `DM-08`, with a reason kind and a message for every outcome that is not `pass` (`CR-31`).
- **HLT-01** (should) Watch each machine's health with its heartbeat: its clocks (`HLT-02`, a must), its frame rate and its answer time, and end a check that overlaps an unhealthy interval `invalid` / `unhealthy` (`CR-30`; conflict C6). The frame rate is the frames over the last 5 s of real time of the machine's heartbeats. The answer time is how long the machine takes to answer the runner's ping: the runner sends a ready machine that is not held a ping with each heartbeat, one at a time, which its agent answers through the path of every order (the extension's callback, a scheduled script, the extension's send), and the answer time is how long the last answered ping took, or how long the ping it has not answered has waited, whichever is longer. The runner flags the machine `frame-rate` when, over the last 5 s of real time, it ran fewer than 10 frames a second, and `answer-time` when its answer time was above 2 s at every heartbeat of those 5 s; a frame number that stands still is named `frame` first, then a frame rate under its floor, then mission time under half of real time (`HLT-02`), then answers that lag. Mission time that crossed while the steps since it crossed ran fewer than 10 frames a second is named `frame-rate`, with the frame rate over those steps: the engine caps the simulation step of each frame, so a machine starved of frames loses mission time. The flag clears once every measure held over a whole 5 s again, and the measure crossed at the first heartbeat that shows it. One floor serves every kind of machine: over 50 passing checks in singleplayer and 50 on a dedicated session with two clients and a headless client no machine's 5 s frame rate fell under 44 and no answer took longer than 0.03 s; a rendering client runs about 58 frames a second while a remote desktop stream shows its window and 18 to 20 while none does; and a client suspended 480 ms of every 500 ms ran 2 to 4 frames a second, its answers under 0.5 s, and was flagged `frame-rate` in 3.6 to 5.6 s, 5 of 5 (`SPK-22`). A check execution that overlaps a flagged interval ends `invalid` / `unhealthy`, naming the machine, the measure and its value, unless a cause for `fail` came first (`DM-06`). `status` shows each machine's frame rate and answer time beside its flag and the clocks of its last heartbeat (`INS-04`). A process that ends is caught by `P-09` and a machine that stops answering by `P-07`; the framework watches no window, which only a hand over (`MAN-01`) needs.
- **HLT-02** (must) From the moment a machine is `ready`, its in-game agent sends a heartbeat every second of real time carrying the clocks of `OBS-05`. The heartbeat is sent from a per-frame handler (the `EachFrame` mission event, gated on `diag_tickTime`), not from a scheduled loop, so it keeps coming while the scheduled environment or the simulation stands still. The runner flags the machine unhealthy when, over the last 5 s of real time, its mission time advanced less than half as much as its real time or its frame number did not advance, and clears the flag once both clocks moved over a whole 5 s again; the clock stopped at the first heartbeat that shows it. A machine whose heartbeat has not come for 10 s has stopped answering, and is `lost` as `P-07` says. The 10 s count only time the runner itself runs: a runner that was paused, suspended or starved for 2 s or more finds the heartbeats sent meanwhile still waiting in its connections, so it judges no gap in that moment and counts every machine's gap from it again (`SES-06`). Over 50 passing checks in singleplayer and on a dedicated session no heartbeat came more than 1.2 s after the one before and no 5 s window ran below 0.99 of real time (`SPK-15`). A check execution that overlaps a flagged interval ends `invalid` / `unhealthy`, naming the machine and which clock stopped, unless a cause for `fail` came first (`DM-06`). `status` shows the flag and the last heartbeat's clocks on the machine (`INS-04`) (`CR-30`, G3; conflict C6).
- **OUT-02** (should) Repeat each selected check N times and summarise each by `DM-09`, with the count of each outcome (`CR-32`). `run --repeat N` (1 to 100) runs each selected check N times in a row, each repeat its own execution with its own reset; the result file gives each check's summary outcome and counts, the command prints a line per check with them, and a run with a `flaky` check exits 1, as for a `fail`. When the session breaks during repeats, the repeat running ends as any check does (`DM-05`), the repeats not started are not run with reason `session-broken`, and the summary counts only the repeats that ran.
- **OUT-03** (could) Run a check marked as expected to fail against a build where its promise is broken, and report it as proven when it fails (`CR-33`).
- **OUT-04** (could) Measure a baseline of the game's own behaviour in the same run and conditions as a check that compares against it (`CR-34`).

## Selecting and running checks

- **RUN-01** (must) A run selects checks by one or more check ids, by one or more tags (a check matches when it carries any of them), or both (the union). A check id given more than once selects that check once per time it is given; a tag selects each check it matches once, and adds nothing for a check also given by id. With no selection it runs every check (`CR-40`).
- **RUN-02** (must) `list` returns every check's id, name, tags, setups, timeout and reset mode from the files, without a runner or a game, filtered like `RUN-01`, each selected check once (`CR-40`, `CR-53`).
- **RUN-03** (must) Checks given by id run in the order given, a check given more than once once per time it is given, so `a a b` runs `a`, `a`, `b` and `a b a` runs `a`, `b`, `a`; checks selected by tag run after them in check id order, and with no selection every check runs in check id order (`CR-40`).
- **RUN-04** (must) A run given a setup when no session runs starts a session of that setup, runs, and stops it, whatever the outcomes, unless a check handed the session over to a manual tester, which leaves it up (`MAN-01`) (`CR-05`, `CR-40`, scenario "as planned" 5).
- **RUN-05** (must) A run can be stopped by hand, with `run stop`, `run_stop`, or a Ctrl+C or Ctrl+Break console event to `shakedown run`, which it treats alike. The check being prepared or executing ends `invalid` / `run-stopped` and its body is terminated in the game, the checks not started are listed as `not-run` / `run-stopped`, the result file is written with `run.state` `stopped` and `stopped_reason` `by-hand`, and `run stop` and `run_stop` return once it is written. A check whose reset or body had ended when the stop came keeps its outcome. A mission restart before a `@reset mission` check runs to its end first, so no machine is left half restarted. A run stopped before its first check, such as by a Ctrl+C while the session it starts is starting, lists every check as not run; the session start itself is not cut short. A run that started its own session stops that session after a stop as after any end (`RUN-04`). `session stop` during a run stops the run first, with `stopped_reason` `session-stopped` (`P-10`) (`CR-05`, `CR-31`, `CR-51`).
- **RUN-06** (must) A run has a runner ceiling of the sum of the timeouts of its check executions plus 60 s, counted from the start of its first check, after any session the run starts is `ready`. The timeouts are read from the checks' headers at the run's start; a check whose `@setups` leaves out the session's setup, or whose header is wrong, adds nothing, since it ends without the game. Resets, mission restarts and cleanups count against it. At it the run is stopped as `RUN-05` says, and the result file gives `stopped_reason` `run-ceiling` (`CR-20`, `CR-05`).
- **RUN-07** (should) Choose the setups per check: a check's `@setups` header names the setups it runs in, a run skips the others as `not-run` / `setup`, and one command runs a selection in each setup it needs, one session per setup (`CR-41`). With no session running, `run --each-setup` runs the selection once per setup that a selected check names, in the order the project file declares them, each as `RUN-04` runs one: its own session, its own run and result file, stopped after it. A check with no `@setups`, or whose header cannot be read, names every setup. Each setup's run holds the selected checks that name that setup, so its result file lists no check as not run for `setup`. A setup whose session start is refused (`SES-03`) or fails (`SES-04`) lists its checks in a result file of its own as `not-run` / `session-failed` with the start's reason, and the next setup still runs. A stop by hand (`RUN-05`) stops the setup's run that is going and starts no further setup; a hand over (`MAN-01`) keeps the setup's session up and starts no further setup. The command prints a line per check execution and a line per setup, and exits with the highest exit code of its runs. With a session running it is refused, naming `session stop`.
- **TIM-01** (should) Report the time of every step and flag steps over a threshold (`CR-42`). Step times are recorded by `OBS-05`. A step that took longer than the project's `slow_step`, a positive number of seconds, 10 by default, and a check execution whose duration was more than half its timeout, are flagged `slow` in the result file and in the line the command prints for the check, which names each slow step with its duration.

## Check API

- **API-01** (must) A check is one `.sqf` file under the tests folder whose first lines are a header of `// @key value` lines: `@check` (the name, required, starting with the story or requirement ID it proves), `@tags`, `@setups` (setups the project file declares), `@timeout` (seconds, default 120) and `@reset` (`in-place` or `mission`, default `in-place`), as the check API contract gives. The rest of the file is the body (`CR-50`, `CR-40`).
- **API-02** (must) The body runs scheduled on the lead machine, as SQF compiled with `compile`, so a check needs no build step and is reloaded on every run (`CR-50`, `CR-03`).
- **API-03** (must) The check API offers, as SQF functions with the prefix `skd_fnc_`: steps; running code on one machine and on a group; waits; immediate and polled assertions on one machine and on several; agreement across machines; expected errors; creating objects and units, placing units, setting time and weather; using an action; pressing a keybind; cleanups; evidence; ending a check as `fail` or `invalid` by hand; and the session's machines and setup. Names, arguments and results are in the check API contract (`CR-50`, `CR-10`, `CR-11`, `CR-12`, `CR-20`, `CR-22`, `CR-23`).
- **API-04** (must) The check API is plain SQF functions: a check needs no `#include`, no macros and no language but SQF (`CR-50`).
- **API-05** (must) The framework's addon does not need CBA. It uses CBA only when a check presses a keybind and CBA is loaded (`CR-50`, `CR-12`).
- **API-06** (should) Checks share helper code through a library folder, `tests/_lib/` by default or the project's `lib`: every `.sqf` file directly in it is compiled once on every machine after each mission start and after each reload, which reads the folder again, and its compiled code is stored in a global variable named `skd_lib_<file name>`, so the body of every check and code sent to any machine can call it with `call skd_lib_<file name>`. `list` and `run` never take a file under the library folder as a check. A library file that does not compile, or whose name is not letters, digits and `_`, ends every check of the run `fail` / `check-error` with the file and line (`CR-50`; `DEF-27`).

## Result file

- **RES-01** (must) Every run writes exactly one result file, `result.json`, in its run folder, valid against the JSON Schema `contract/result.schema.json`, also when the run was stopped or its session broke (`CR-51`).
- **RES-02** (must) The result file holds the run and session ids, the setup with its machines, the game build and each mod's version as each machine loaded it, the selection, every check execution with its outcome, reason, steps with times, script errors, evidence and reload state, the reloads during the run, the checks not run with the reason, and the summary counts (`CR-51`, `CR-42`, `CR-23`).
- **RES-03** (must) Evidence for an outcome that is not `pass` includes the failed step's path, the last observed value per machine, every unexpected script error, the values the check attached, and the paths to each machine's log excerpt for that check (`CR-51`, `CR-23`).
- **RES-04** (must) Paths in the result file are relative to the run folder (`CR-51`).
- **RES-05** (must) Every reason of an outcome that is not `pass` carries the wall-clock time of the cause that decided it, and every machine that was `lost` carries the wall-clock time it was lost, so the order `DM-06` judges by is in the result (`CR-51`, `CR-31`).

## Agent tools

- **AGT-01** (must) `shakedown mcp` is an MCP server over stdio, declared for Claude Code in the project's `.mcp.json`, that gives an AI agent every capability of the command line as tools with the same results (`CR-53`).
- **AGT-02** (must) Every tool has an `outputSchema` and returns `structuredContent` and the same JSON as text. A check that fails is a successful call that returns the outcome. `isError` is used only for what the AI agent can fix (unknown check, unknown machine, code that does not compile, no session, an expired handle), and the message says what to do next (`CR-53`).
- **AGT-03** (must) No tool call outlasts 60 s. A run returns a run handle at once and is followed with `run_status` and `run_result`; a wait or an `exec` takes a ceiling of at most 50 s. A call that waits sends progress notifications at least every 5 s when the client gave a progress token (`CR-53`, `CR-20`).
- **AGT-04** (must) A cancelled tool call stops the game-side work it started (`CR-53`).
- **AGT-05** (must) The MCP server starts and answers `status` on a machine without the game or without a runner, saying so, instead of failing to start (`CR-53`).
- **AGT-06** (must) A `guide` tool returns a short text on how to use the tools and write a check, for clients that do not load the project's docs (`CR-53`).
- **AGT-07** (must) Tool results stay under 20,000 characters; anything longer is written to a file in the project's `.shakedown/results/` folder, which serves every tool whether or not it has a session or a run, and the result gives its path (`CR-53`, `CR-24`).

## Safety

- **SEC-01** (must) The runner listens on `127.0.0.1` only. Every client presents the runner token from `runner.json` on each connection, and every extension presents its session token; a connection with anything else, or whose first message is not the protocol's hello, is closed (`CR-60`).
- **SEC-02** (must) The session token is a random 256-bit value made per session and passed to each game process only in its environment, never on a command line. The runner token file is readable by the current user only (`CR-60`).
- **SEC-03** (must) The runner accepts an extension's hello only from a process id it started for that machine of that session. It takes the process id of the connection's other end from the system's TCP table (`GetExtendedTcpTable`), never from the hello, so a process that holds a stolen token still cannot pose as a game process (`CR-60`).
- **SEC-04** (must) Every `exec` order, from a client or from a check, is appended to `audit.jsonl` in the session folder with its time, source (`cli` for the command line, `mcp`, or the check id), target and code. From a check that is its body, sent to the lead, and each piece of code the body sends to another machine through the runner (`skd_fnc_on`, a wait or a polled assertion); code the body runs on the lead itself is part of the body. The code is redacted as everything else the runner stores (`LOG-02`) (`CR-60`, `CR-53`).
- **SEC-05** (should) Refuse to start with BattlEye on or against a server that is not the session's own loopback server (`CR-61`). Every `server.cfg` the framework generates has `BattlEye = 0` and `loopback = 1`, and every game process starts from the game's own executables without its BattlEye launcher (`NFR-LG-02`), so no start of the framework's runs with BattlEye or joins another server. The one way left is code a check sends: a client whose in-game agent finds itself in a mission whose server is not the session's (`hostname = "shakedown <session id>"`, `INT-AR-05`) is ended at once: its agent reports the server's host name to the runner instead of `ready`, the runner ends its process and marks it `lost` with reason `foreign-server`, the session goes `broken` with that reason, and the check ends `fail` / `check-error` saying a client may join only the session's own server (`DM-04`, `P-07`).
- **SEC-06** (must) The runner token is `skd_r_` and the session token `skd_s_`, each followed by 64 lowercase hexadecimal digits of the random value. The fixed form lets any leak be found by searching for the pattern, in command lines, files, logs and tool output (`CR-60`).

## Release and install

A release is the framework built once, from a tag, for 64-bit Windows, and installed by winget, by a one-line script or by hand (research `34-release-and-licence.md`). `tools/install.py` stays the install from source, and the only one that builds the fixture mods. On macOS and Linux the binary is still built with cargo (`NFR-PT-02`).

- **DST-01** (should) Pushing a tag `v<version>` whose version equals the workspace version in `Cargo.toml` builds one GitHub release of that version. It holds `shakedown-windows-x64.zip`, its SHA-256 in `shakedown-windows-x64.zip.sha256`, and `install.ps1`. The zip holds `shakedown.exe`, `@shakedown\` with `addons\shakedown_main.pbo` and `shakedown_x64.dll`, `LICENSE` and `THIRD-PARTY-LICENSES.txt` (`NFR-LG-04`), and nothing else: no fixture and nothing that needs the source to run. A tag whose version differs from the workspace version fails the release workflow and publishes nothing. A version with a pre-release part, such as `0.2.0-rc.1`, publishes a GitHub pre-release, which `releases/latest` never names, and submits nothing to winget (`CR-70`).
- **DST-02** (should) winget installs a release as the package `casvanluijtelaar.Shakedown`, with a manifest of type `zip` and `portable` whose nested file is `shakedown.exe`, so `@shakedown\` lands next to the binary and `shakedown` is on `PATH`. `winget upgrade` installs a newer release and `winget uninstall` removes it. The first version is submitted by the owner; the release workflow submits every later one (`CR-70`).
- **DST-03** (should) `irm https://github.com/casvanluijtelaar/shakedown/releases/latest/download/install.ps1 | iex` installs the latest release for the current user, with no administrator rights: it downloads the zip and its `.sha256`, refuses a zip whose SHA-256 differs and changes nothing, unpacks it into `%LOCALAPPDATA%\Programs\Shakedown`, and adds that folder to the user's `PATH` once. With `$env:SHAKEDOWN_VERSION` set, such as `0.2.0-rc.1`, it installs that release instead of the latest. Run again, it replaces the installed version with the latest. While any `shakedown.exe` from that folder runs, the runner or an AI agent's `shakedown mcp` among them, it refuses before it changes any file, naming each such process by its id and command, and says to stop them first (`CR-70`).
- **DST-04** (should) The zip unpacked by hand into any folder is a complete install: `shakedown.exe` finds `@shakedown\` next to itself, and putting the folder on `PATH` is the one step left (`CR-70`).

## Fixture mods

The framework is developed and accepted against fixture mods of its own, whose promises are [contract/fixture-mod.md](contract/fixture-mod.md). Besides a target for each capability, they give a test the failures of the environment it cannot otherwise cause on purpose. They are test targets, never part of the framework: a session loads them only when its setup names them, like any mod.

- **FIX-01** (must) A fixture function crashes the game process it runs on, after a delay in real time, through a fault in native code, so the engine's own crash handling runs, writes its crash dumps and ends the process unasked; a process that handling leaves running 5 s after the fault is ended by the fixture's extension with the exit code of an access violation, as a headless client sometimes is for a minute (`SPK-16`); another ends the process with a chosen exit code after a delay. A check places a crash at a known point between its own steps (`CR-31`, G3; `SPK-16`).
- **FIX-02** (must) A fixture function holds singleplayer `p1`'s mission time still for a given number of seconds of real time while its frames go on and it keeps answering, as when the Shadow stream is cut, then lets it run, by setting the engine's time acceleration to 0 and back to 1 (`CR-30`, G3; `SPK-17`).
- **FIX-03** (must) The fixtures name the files a test may change in their installed copy for a reload, and when: the two reload targets, changed only while no game process holds them, by a mod's `rebuild` during a reload once every game process has ended or the reload has freed them (`RLD-06`), or with no session running; one file absent from the build that a test may create and must delete after; and any installed fixture file a test may name to `reload` without changing it (`CR-03`).
- **FIX-04** (must) A fixture function makes the game process it runs on hold a file of the game folder open for reading only, as the game holds a loose file it read, until the process ends, so a test can make a reload find a changed file still held after the release files were read (`CR-03`; `US-082`).

## Further should and could requirements

- **MCH-01** (should) Make a machine leave, join late, rejoin, or restart the server during a session, and wait on the server's own events with a ceiling set from the disconnect timeout (`CR-04`). For game clients on a dedicated session:
  - A setup declares late clients with `late`, a count of game clients that the session does not start; they are named after the clients it starts, so `clients = 2` and `late = 1` give `p1`, `p2` and the late `p3`. The session mission and `server.cfg` hold a slot for every late client (`INT-AR-04`, `INT-AR-05`). `status` lists a machine only while its process runs (`INS-04`), and `skd_fnc_machines` once it is `ready`.
  - `skd_fnc_join [machine, ceiling]` starts a late client or a client that left and returns once it is `ready` (`P-02` step 7), within the start ceiling by default. A client that rejoins gets the next start number of its role. A join that does not reach `ready` within its ceiling ends the check `invalid` / `machine-lost` naming the machine and its last 20 RPT lines, stops the process it started, and leaves the session `ready` without it.
  - `skd_fnc_leave [machine, ceiling]` makes a client leave and returns once the server's `PlayerDisconnected` event has fired for it, within a ceiling of the server's disconnect timeout plus 5 s by default, 20 s with the default timeout of 15 s. The server kicks the client by its profile name while its process still runs, which drops it at once, and the runner then ends its process; a client the server has not dropped within 5 s has its process ended and is seen go at the disconnect timeout (`SPK-18`). The machine is then `stopped`, not `lost`, so no check is `invalid` for it. A leave that the server has not seen within its ceiling ends the check `invalid` / `machine-lost` naming the machine.
  - Joining or leaving `server`, a headless client, a machine the setup does not name, a client already in the session or one already out, or any machine in singleplayer, ends the check `fail` / `check-error` naming the machines that can join or leave (`DM-04`).
  - The reset before the next check, and the `reset` command, first bring the session back to the machines it started with: a late client that joined leaves, and a client that left joins again (`P-06`). The unit a client leaves behind when it leaves, a body with the session mission's `disabledAI = 1`, is deleted by that reset, so a client that joins again at the same start position stands alone there. That restore has the start ceiling per join; the reset in place after it keeps the ceiling of `RST-04`. A restore that does not complete fails the reset (`RST-04`, `DM-05` `reset-failed`). A check with `@reset mission` has the restore before its mission restart.
  - Restarting the server during a session waits for use to show it matters (`DEF-31`).
- **ENV-01** (should) Check the environment before a run in full: Steam logged in, each mod present in the version the project names, free disk, and report each gap (`CR-06`). Steam counts as logged in when its login file names an account (`INT-STM-04`) and Steam's `ActiveUser` value is not 0 (`INT-STM-01`), and free disk is at least 2 GB on the drive of the project's `.shakedown/` folder; the start checks both with `SES-03`, before any process starts, and lists every gap it found, not only the first. A mod with a `patch` may name its `version` in the project file, the exact `versionStr` of that class: once the machines report the versions they loaded (`INT-STM-03`), a start in which any machine loaded another version, or does not load the class, fails, stops every process it started, and names the mod, the machine, the version found and the version wanted, so no check runs against it.
- **RSM-01** (could) Resume a run from the last finished check after a reboot or a game crash (`CR-07`).
- **CHT-01** (could) Act as a cheating client: send forged, repeated or out-of-role requests and events from one machine (`CR-13`).
- **FLT-01** (could) Simulate failures: kill a client, add lag or packet loss, stall a frame, make a unit unconscious, kill and respawn it (`CR-14`; conflict C4, scenario "things go wrong" 7).
- **SHT-01** (could) A screenshot check that captures chosen steps on a rendering client and returns the images with what they were expected to show, with no verdict of its own (`CR-25`; conflict C5).
- **PRF-01** (could) Measure frame time on every machine and the cost of a mod function on the server and a client (`CR-26`).
- **MAN-01** (should) Put a manual tester at the start of a situation set up by a check, with a list of what to look for, and leave the session up for them (`CR-52`). The check calls `skd_fnc_handOver [machine, items]` on a game client, with one to ten things to look for: the list is shown on that client's screen until the next reset, at the top centre, where the game's default HUD layout leaves the action menu, the communication menu and the elements at the top right free, the body ends there, and the check's outcome is fixed as for a check whose body reached its end. A check that ends `pass` is recorded as handed over, with its machine and its items; the checks of the run after it are not run, with reason `handed-over`; the command and `run_result` give the machine whose window to use, the items and the command that ends the session; no reset follows; and the session stays up, `ready`, also in a run that started its own session, until the next run, reset, reload or `session stop`. In `run --each-setup` the hand over keeps that setup's session and starts no further setup. A check that ends otherwise, such as `fail` / `script-error` for an error raised before the hand over, is not handed over, and the run goes on as usual. A hand over to `server` or a headless client ends the check `fail` / `check-error`, naming the game clients it can hand over to.
