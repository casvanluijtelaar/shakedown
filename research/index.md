# Research

* [Research plan](00-plan.md) - The topics the research covers before the spec is written, the questions each must answer, its output file, its verification gate and whether the MVP waits on it.
* [Best of breed](01-best-of-breed.md) - For each capability the framework needs, which tool or idea it takes, which it rejects and why, with the license that decides whether code can be reused.
* [Gaps between the PRD and the research](02-gaps.md) - The holes the PRD leaves that the research shows matter, the places where a requirement conflicts with what the engine allows, and the open questions for the owner, each with a recommendation.

* [Running code in the game from outside](12-remote-execution.md) - Which channels carry SQF from a process outside Arma 3 into a running game and a result back, on which machines they work, their limits, how code reaches a chosen machine, and which language each one forces on the framework's internals.
* [Hot reload of mod code and checks](13-hot-reload.md) - What of a mod and of the checks can be reloaded into a running Arma 3 session without a game restart, what file patching needs on each machine, how CBA, ACE and HEMTT developers reload today, and what forces a restart.
* [Sessions: starting, keeping and resetting the game](14-sessions.md) - How singleplayer, a dedicated server, clients and headless clients start from the command line, how many checks can run in one session and how its state is reset, what joining, leaving and mission changes do, and how fast each path is.
* [Making a player act: actions, key handlers and key input](15-player-input.md) - How a check moves, turns and aims a player, uses a mod's addAction, ACE interaction and CBA keybind paths from code, whether key input can reach one game window without taking the desktop, and how a scene is built and removed.
* [Observing the game: waits, events, errors, logs, screenshots](16-observation.md) - How a check waits for a condition with a ceiling, which engine and CBA events it can collect per machine with timestamps, how script errors are caught live and tied to a step, where each machine's log is, how screenshots are taken, and which performance probes exist.
* [Health, stalls and clean stops](17-health.md) - How the framework tells a healthy session from a stalled one, what the game does without focus or a visible window, how every process a run started is stopped even when the runner crashes, how the environment is checked before a run, and how a crash is told from a stop.
* [Test automation tools for the web, mobile and games](18-test-tools.md) - How Playwright, Maestro and the game test tools shape a test, wait on a running app, retry, filter and report, and what of each fits a check written in SQF.
* [Agent tools: MCP](19-agent-tools.md) - What the current Model Context Protocol, Claude Code's MCP loading, Playwright's MCP server and the Arma MCP servers say about how the framework exposes its capabilities to an agent, and how to run that server safely on the local machine.
* [Licenses, the EULA and Bohemia's rules](20-licenses-and-rules.md) - What the Arma 3 EULA, Bohemia's tools license and content rules, Steam's terms, the BI wiki's terms and the licenses of CBA, ACE3 and the T2 tools allow a test framework to do, and what personal data its logs hold.
* [What mod developers say about testing](21-mod-developer-pain.md) - A short first pass on what Arma 3 mod and mission developers report about testing their work, the workarounds they use and the failures that keep coming up, from GitHub issues, the Bohemia forums and Reddit.
* [Spikes SPK-01, SPK-02 and SPK-03 in singleplayer](22-spikes-singleplayer-channel.md) - What the round trip through the extension and its callback, large orders and results, and the session token through the environment measured on singleplayer p1 on the test machine in M0, with the engine facts the walking skeleton found on the way.
* [Spikes SPK-04, SPK-05, SPK-10 and SPK-12 in singleplayer](23-spikes-singleplayer-reset.md) - What the reset in place, the player's death and endMission under -autotest, an action fired with action User, and net ids measured in a singleplayer session on the test machine in M1, with what CBA's keybind registry and a created vehicle showed on the way.
* [Spikes SPK-01, SPK-03 and SPK-04 on a dedicated session](24-spikes-dedicated.md) - What the round trip through the extension and its callback and the session token through the environment measured on a dedicated server, a game client and a headless client, and what the reset in place measured over 20 checks on a dedicated session with two clients and a headless client, on the test machine in M2, with the engine facts found on the way.
* [Spikes SPK-07 and SPK-13: script errors and live RPTs](25-spikes-errors-and-logs.md) - What the ScriptError mission event caught on a singleplayer p1, a dedicated server, a game client and a headless client for every kind of code against what each RPT showed, and how soon a reader beside a running game sees a diag_log line in its RPT, on the test machine in M3, with the RPT's error format and what taking the value of code that ends in an assignment does, found on the way.
* [Spike SPK-06: the runner outlives its client and dies with its game](26-spike-runner-detach.md) - How Claude Code holds and ends a stdio MCP server on Windows, which way of starting the runner leaves the client's job and process tree, that a dedicated session started from one Claude Code session is found ready by the next, and how fast the game ends when the runner is killed, on the test machine in M5.
* [Spikes SPK-08 and SPK-01 across a mission restart: reloading by restart](27-spikes-reload.md) - What a changed mod file does in a running game on the test machine in M6 - the game holds every loose file it read until some time later that no wait or flush tried here controls, a released file reaches even a kept process through a mission restart, and SPK-08 holds once in singleplayer and once on a dedicated session but not as a promise - with what ACE3, HEMTT and Neefay's harness actually do to reload, CBA's cache shown off, the time of a mission restart in singleplayer and on a dedicated session, and orders sent across mission restarts, none lost and none run twice.
