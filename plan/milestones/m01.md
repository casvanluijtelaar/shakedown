# M1 A grappling-hook check in singleplayer

## Goal

Put the framework in the owner's hands on arma-grappling-hook as early as possible. A test author writes checks that build a scene, act through the mod's real path, wait and assert, and runs many of them in one singleplayer session, each from the session's start state.

## Demo

The arma-grappling-hook story `US-009` (let go at any height), rewritten as a Shakedown check, passes in a singleplayer session with CBA: it places a rope with the mod's public function, gets `p1` on it through the mod's `Get on rope` action, presses the mod's let-go keybind and waits until `p1` is off the rope.

## Stories

- `US-018` (mistake) An unknown class name or a wrong argument to the check API
- `US-021` (feature) Make a player press a mod's CBA keybind
- `US-022` (mistake) A keybind that is not registered, or a setup without CBA
- `US-039` (error) A check runs past its timeout

## What it builds

- The check API of the contract for a singleplayer session: `skd_fnc_on` and `skd_fnc_onEach`, `skd_fnc_waitUntil` and `skd_fnc_tryWaitUntil`, `skd_fnc_expectOn`, `skd_fnc_expectEach`, `skd_fnc_expectAgree`, `skd_fnc_create`, `skd_fnc_place`, `skd_fnc_setDate`, `skd_fnc_setWeather`, `skd_fnc_useAction`, `skd_fnc_pressKey`, `skd_fnc_cleanup`, `skd_fnc_invalid`, `skd_fnc_machines`, `skd_fnc_setup` and `skd_fnc_player`, with the argument checks of `DM-04`, the check timeout and the ceilings.
- Values across the channel as `DM-13` and `DM-14` say.
- The reset in place of `P-06` in singleplayer, with the entity recorder (`SCN-04`), the baseline (`RST-02`) and the player brought back after death (`RST-05`).
- `session start` and `session stop` on the command line, runs against a running session (`SES-05`), and the selection by ids and tags (`RUN-01`, `RUN-03`).
- The fixture mods `@skd_fixture` (loadable on its own) and `@skd_fixture_cba` with its keybind, installed as `contract/fixture-mod.md` says.
- `e2e/grappling-hook/`: a `shakedown.toml` naming CBA and the arma-grappling-hook development build, and the demo check.
- `docs/`: every check API function above, with an example.

## Spikes

- **`SPK-04`**, its singleplayer half, runs before the work that depends on it; its pass condition is in `spec/06-open-questions.md`. If it fails: What the reset cannot restore is listed in the check API contract as needing `@reset mission`, and `NFR-PF-04` is set from the measurement. That changes the contract: a check that changes such state must ask for a mission restart. Its dedicated half runs in M2.
- **`SPK-05`**, whole, runs before the work that depends on it; its pass condition is in `spec/06-open-questions.md`. If it fails: The first fallback, a `Killed` handler that hands `p1` a new unit, changes no promise. The second, starting the session with `-init=playMission` instead of `-autotest`, makes a level-B reload in singleplayer a game restart: `RLD-02`, `P-08` and the singleplayer half of `US-055` change, and M6 delivers that instead.
- **`SPK-10`**, whole, runs before the work that depends on it; its pass condition is in `spec/06-open-questions.md`. If it fails: `ACT-01` checks the condition and radius itself either way. No promise changes.
- **`SPK-12`**, whole, runs before the work that depends on it; its pass condition is in `spec/06-open-questions.md`. If it fails: The agent keeps its own table from a counter to the object in singleplayer, and the `netId` of `DM-13` carries that counter there. A singleplayer result then shows the agent's ids, not the engine's net ids; `DM-13` is edited to say so.

## Exit criteria

1. `US-018`, `US-021`, `US-022` and `US-039` pass their acceptance criteria on the test machine.
2. The demo check passes 10 times out of 10, in one run together with a second check, against one session.
3. A run of 20 checks in one singleplayer session, each creating units, vehicles and objects and changing time, weather and the player, passes with every check seeing the start state (the singleplayer half of `NFR-RL-02`).
4. The spikes' results are in `research/`, and the spec is edited in place to what they found.
5. Every check and test it adds carries the story or requirement ID it proves (`NFR-MT-02`), the gates of `NFR-MT-03` pass, and `docs/` say how to use what it built.
6. The owner has run the demo on the Windows test machine.

## Left out

Dedicated sessions and everything across machines (M2). `skd_fnc_useAction` is built here because the demo needs it; its stories, `US-019` and `US-020`, name a dedicated session and land in M2. The `reset` command (M2). Script errors and logs (M3).
