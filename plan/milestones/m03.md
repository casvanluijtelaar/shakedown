# M3 Script errors and logs

## Goal

Make a verdict on arma-grappling-hook explain itself. A pass means no script error on any machine; a failure carries the step it happened in, the last value each machine showed, the script errors with their machine and step, and each machine's log for that check. Nothing a run leaves behind names the Steam account the game runs on.

## Demo

The M2 grappling-hook check, with its last assertion changed to one the mod cannot meet, fails with its step, each machine's last value and log excerpt in the run folder, and any script error the mod raised with its machine and step, and a search of the run folder finds no Steam ID or Steam name.

## Stories

- `US-024` (error) A condition that is never met
- `US-027` (feature) A check of an error path expects a script error
- `US-028` (error) The mod throws a script error on one client only
- `US-029` (error) An expected script error never comes
- `US-030` (system fail) A script error the in-game handler misses still reaches the result
- `US-064` (feature) A run's result file and stored logs hold no Steam name and no Steam ID
- `US-065` (mistake) A check puts the Steam ID or the Steam name into its result

## What it builds

- The `ScriptError` handler on every machine and the attribution of `P-05` steps 6 and 7 (`ERR-01`), the outcome rule of `ERR-03`, and `skd_fnc_expectError` (`ERR-04`).
- The RPT scan (`ERR-02`, `INT-AR-07`).
- The cause of the server's `Object ... not found (message Type_189)` line after a reset on a dedicated session, fixed at its source so the line is not logged (`DEF-09`).
- The run's and each check's log excerpts with the agent's markers (`LOG-04`), the `logs` command (`LOG-03`), and the evidence of `RES-03` and `OBS-04`.
- Redaction of Steam IDs and the account's names (`LOG-02`, `INT-STM-04`) in the result file, the run folder, command output and stopped sessions' RPTs.
- The fixture's `skdfx_fnc_throw`.
- `docs/`: script errors, expected errors, reading logs and evidence.

## Spikes

- **`SPK-07`**, whole, runs before the work that depends on it; its pass condition is in `spec/06-open-questions.md`. If it fails: The RPT scan becomes the primary source on the machine kinds where the handler is silent, and errors there are attributed by time only. That changes the promise for those kinds: their errors come with `source` `rpt` and the step running on the lead at that time, as `US-030` shows, not the step stamped on the machine as `US-028` shows.
- **`SPK-13`**, whole, runs before the work that depends on it; its pass condition is in `spec/06-open-questions.md`. If it fails: `logs` and the RPT scan read a machine's RPT only after the check ends or the session stops, and `INS-01`'s errors come from the handler alone. That changes `LOG-03` and `INS-03`: `logs` asked during a check returns the lines up to that check's start.

## Exit criteria

1. `US-024`, `US-027`, `US-028`, `US-029`, `US-030`, `US-064` and `US-065` pass their acceptance criteria on the test machine.
2. Over the milestone's acceptance runs, every script error the RPTs show from mission start on is in a result file (`NFR-RL-05`).
3. The spikes' results are in `research/`, and the spec is edited in place to what they found.
4. Every check and test it adds carries the story or requirement ID it proves (`NFR-MT-02`), the gates of `NFR-MT-03` pass, and `docs/` say how to use what it built.
5. The owner has run the demo on the Windows test machine.

## Left out

The `logs` and `errors` tools and the `errors` command (M4). The logs of a machine that crashed (M9). Crash dumps are copied unredacted (deferred 03).
