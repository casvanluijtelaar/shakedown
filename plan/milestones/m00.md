# M0 Walking skeleton

## Goal

Prove the whole chain once, end to end, in the simplest setup: the `shakedown` binary and its runner, the extension, the `@shakedown` addon with the in-game agent, a check file, a result file, and a session that is started and stopped again. Every later milestone grows one of these parts; none of them is built twice.

## Demo

On the test machine, `shakedown run --setup sp smoke` starts Arma 3 in singleplayer, runs one SQF check with steps that passes, writes `result.json`, and stops the game.

## Stories

- `US-037` (feature) Write a check in SQF with steps, named by the story it proves
- `US-038` (mistake) A broken check is the author's to fix

## What it builds

- The source code folders of `spec/07-tech-stack.md`: the Rust workspace with `crates/shakedown`, `crates/shakedown-ext` and `crates/shakedown-protocol`, the HEMTT project `addon/`, and `e2e/` with a `shakedown.toml` and the smoke check. The line in `CLAUDE.md` that lists the source code folders names them.
- The runner as `P-01` starts it: detached, `runner.json` with its token (`SEC-06`), its job object with kill-on-close, every game process started suspended, assigned and resumed (`STP-01`).
- A singleplayer session only: the preconditions of `SES-03` a singleplayer start needs, the session mission and `-autotest` list of `INT-AR-04`, the options of `INT-AR-02`, `ready` (`P-02`), and `P-10` to stop it.
- The channel: the extension's three calls (`INT-AR-03`), the hello with the session token (`SEC-01`, `SEC-02`), orders fetched in parts and results sent in one call.
- The in-game agent's start, its `ready`, the `check` order, and the first check API functions: `skd_fnc_step`, `skd_fnc_on` to the lead itself, `skd_fnc_expect`, `skd_fnc_evidence`, `skd_fnc_fail`.
- The check header (`API-01`), `list` (`RUN-02`), `run <ids> --setup` starting and stopping its own session (`RUN-04`), and the result file (`RES-01`, `RES-02` for the fields that exist, `RES-04`) in `.shakedown/` with its `.gitignore` (`CFG-02`).
- The GitHub Actions gates of `NFR-MT-03`: the bundle check, `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test` on Windows and Linux, and `hemtt check` on the addon. A test validates every result file the tests write against `result.schema.json`.
- `docs/`: installing the framework, the project file's keys a singleplayer setup needs, writing and running a check with the functions above.

## Spikes

- **`SPK-01`**, its singleplayer `p1` part, runs before the work that depends on it; its pass condition is in `spec/06-open-questions.md`. If it fails: The fallback routes orders through the server's agent, and a singleplayer session has no other machine, so there is no fallback for `p1`: the milestone stops and the channel goes back to research. Its server, client and headless client parts run in M2, and its part across a mission restart in M6.
- **`SPK-02`**, whole, runs before the work that depends on it; its pass condition is in `spec/06-open-questions.md`. If it fails: The part size of `INT-AR-03` is lowered until the frame limit holds. No promise changes.
- **`SPK-03`**, its singleplayer `p1` part, runs before the work that depends on it; its pass condition is in `spec/06-open-questions.md`. If it fails: The runner writes a token file per machine into its profile folder and `SEC-02` is edited. The promise that no token appears on a command line or in output holds; only where the token lives changes. Its other machine kinds run in M2.

## Exit criteria

1. `US-037` and `US-038` pass their acceptance criteria on the test machine.
2. The demo runs 5 times in a row; after each run no `arma3_x64` process is left, and the runner exits by itself within 70 s of the last session stopping (`P-01`).
3. The gates of `NFR-MT-03` run on every push to `main` and pass.
4. The spikes' results are in `research/`, and the spec is edited in place to what they found.
5. Every check and test it adds carries the story or requirement ID it proves (`NFR-MT-02`), the gates of `NFR-MT-03` pass, and `docs/` say how to use what it built.
6. The owner has run the demo on the Windows test machine.

## Left out

Dedicated sessions, the reset, every check API function not named above, script errors, logs, `status`, the MCP server. Each comes with the first milestone whose story or demo needs it.
