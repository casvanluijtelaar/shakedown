# M2 Dedicated sessions

## Goal

Run the same checks where arma-grappling-hook's promises live: on a dedicated server whose authority the clients follow. A check addresses every machine by its name, runs code and waits on any of them, and asserts that they agree.

## Demo

The arma-grappling-hook check of its story `US-009` with a freed rope, rewritten, passes on a dedicated server with two clients: `p1` gets on a placed rope through the mod's action and lets go with its keybind, and the server and both clients agree the rope is free.

## Stories

- `US-002` (feature) Start a dedicated server with clients and headless clients in one command
- `US-004` (system fail) A start that never becomes ready ends failed and leaves nothing running
- `US-008` (feature) Every check starts from the session's start state
- `US-009` (error) The previous check killed the player
- `US-017` (feature) Build a scene: objects, units, a player's position and facing, time and weather
- `US-019` (feature) Make a player use a mod's action and check the result on every machine
- `US-020` (error) The action cannot be used
- `US-025` (feature) Assert that every machine agrees with the server
- `US-026` (error) One machine disagrees with the others

## What it builds

- `P-02` for a dedicated setup: `server.cfg` (`INT-AR-05`), the mission copy in `MPMissions`, the server with `-autoInit`, the clients and headless clients started at once, a client `ready` at client state 10 (`INT-AR-09`), and the addon's junction (`INT-AR-06`).
- Orders between machines routed through the runner (`P-03`), and the groups `all`, `clients` and `headless` (`DM-12`).
- The reset of `P-06` on every machine, with the respawn of a dead player on a dedicated session, and the `reset` command on a `ready` session (`RST-03`).
- A start that fails (`SES-04`), and `status` listing each machine from its launch with its process id and profile folder (`INS-02`, `INS-04`; the health fields stay `null` until M9).
- The fixture's crate with its action and its replicated flag.
- `docs/`: dedicated setups, machine names and groups.

## Spikes

- **`SPK-01`**, its server, client and headless client parts, runs before the work that depends on it; its pass condition is in `spec/06-open-questions.md`. If it fails: A machine kind whose callback does not fire gets its orders through `remoteExec` from the server's agent, and `P-03` is edited. A check sees no difference; `NFR-PF-03` is measured over that route.
- **`SPK-03`**, its server, client and headless client parts, runs before the work that depends on it; its pass condition is in `spec/06-open-questions.md`. If it fails: As in M0: a token file per machine, and `SEC-02` is edited.
- **`SPK-04`**, its dedicated half, runs before the work that depends on it; its pass condition is in `spec/06-open-questions.md`. If it fails: As in M1: what the reset cannot restore needs `@reset mission`, written into the check API contract, and `NFR-PF-04` is set from the measurement.

## Exit criteria

1. `US-002`, `US-004`, `US-008`, `US-009`, `US-017`, `US-019`, `US-020`, `US-025` and `US-026` pass their acceptance criteria on the test machine.
2. The demo check passes 10 times out of 10 against one dedicated session with two clients.
3. 20 checks in one dedicated session with two clients and one headless client each see the start state on every machine, and the reset takes under 2 s (`NFR-RL-02`, `NFR-PF-04`).
4. The M1 demo check passes unchanged in the dedicated setup where its promise allows.
5. Every check and test it adds carries the story or requirement ID it proves (`NFR-MT-02`), the gates of `NFR-MT-03` pass, and `docs/` say how to use what it built.
6. The owner has run the demo on the Windows test machine.

## Left out

`@reset mission` and every mission restart (M6). A machine that stops answering or crashes (M9). Script errors (M3).
