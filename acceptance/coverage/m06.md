# M6 Reload by restart: coverage

The `nosteam` and `claude` checks are not part of a run without `--check`. Free memory was 10.9 GB before the `slow` session and 11.2 GB after the `US-035` sessions.

The 7 failures were the machine and the harness, not the framework:

- The first `ded` start of `US-004`, the one that ends `p2`, never got past the server: the server's RPT ends `Error 20 reading file '...\expansion\addons\rocks_f_exp.pbo'` and `Application terminated intentionally`, a base-game file, as the playbook records for this machine. That start failed at its 180 s ceiling with nothing to end, so `US-004 SES-04 a client ended during the start ...` failed ("status never listed p2 with a process id during the start") and `INS-04 m02-1 ...`, which judges that start, failed with it.
- `US-004 SES-04 a setup with start_timeout 30 ...` judged the last status it saw, which was taken after the start had failed and listed every machine `stopped`, while the server had been `ready` before the ceiling; the framework's message named the three machines that were not ready. A mistake of the check: it judges the last status of a starting session. Fixed in the commit that records this run.
- The second of the five `US-035` tries: `p2`'s game hung in its start, its RPT silent from 2 min before the ceiling with no extension connected, and the start failed at 180 s naming `p2`. The four `US-035` checks judge all five tries, so all four failed.

`--check US-004 --check "INS-04 m02-1" --check US-035` right after, with the fixed check, at 19:28Z to 19:37Z: 8 of 8 passed, the five kills at 0.85 to 0.87 s.

[m06-1](../findings/m06/01-a-reset-on-a-dedicated-session-failed-once-on-p2s-direction-and-broke-the-session.md) is verified: `--check "US-008 RST-03 ..." --repeat 3` passed 3 of 3 in one `ded` session against the fix, nine resets at 0.78 to 0.84 s. ## The M6 round

`python acceptance/run.py --repeat 3 --check US-011 --check US-012 --check US-040 --check US-055 --check US-056 --check US-057 --check NFR-PF-02`, which selects the 16 checks of M6 and nothing of an earlier milestone, against the framework installed from `679c79e`, the last commit that changed code, at `89efd87`. The batch runs three times in one session of the setup `rld`: 48 of 48 passed, from 12:24 to 12:40 local time. Each repeat made five game restarts and two mission restarts, and ended `p2` twice by its process id: once during the mission restart of `US-012`, once during the game restart of `US-057`. A run of one repeat before it passed 14 of 16; the two failures were a mistake of the checks (a `\"` in an SQF string, which SQF does not escape), fixed before the three repeats. Two session starts before that died before the session was ready, each on `Error 20 reading file` of a base-game PBO (`missions_f_exp_video.pbo`, then `music_f_oldman_music.pbo`) that read end to end at once afterwards: the machine, as the playbook records, not the framework.

Every `rld` session is a dedicated server, two clients and a headless client loading CBA_A3 and both fixtures. `@skd_fixture` is watched in its installed copy; `@skd_fixture_cba` in a staged copy of its installed sources in the project, with the `rebuild` of `fixture-mod.md` that copies the staged `fnc_version.sqf` into the installed copy. The installed copy was `"1"` and held no `fn_new.sqf` after every repeat and after the session stopped.

## Stories and criteria

- **US-040** Edit a check and rerun it: the check edited from `== 1` to `== 2` failed `assertion` with the new expectation in its message, the machines kept their start numbers in both result files and in `status`, and the outcome came 0.6 s after the save (`NFR-PF-01`, under 30 s), three times. `shakedown reload checks\m06\US-040-edit.sqf --json` and the `reload` tool with the same file, relative to the project, each answered level `none`, the file's reason saying checks are read fresh for every execution, at once.
- **US-011** A mission restart before a check: a check set `acc_m06_flag` public on the server and saw it on every machine; the `@reset mission` check after it saw it `nil` on every machine and passed. The run's result file lists `p1`, `p2` and `hc1` each at its old start and one higher, the server once, every last start `ready`; the run took about 50 s, the mission restart most of it.
- **US-012** A mission restart that loses a machine: `p2`'s new process was ended by its id 10 to 18 s into the run, while the mission restart before the `@reset mission` check waited for it. That check ended `invalid` / `reset-failed` naming `p2`, the next `invalid` / `session-broken`, the run exited 2, and its result file is valid against `result.schema.json`. `status` showed the session `broken`; `shakedown reload` with nothing changed brought every machine back `ready` with a higher start number, level `game-restart`.
- **US-056** A change that needs a rebuild: `fn_new.sqf`, created in the installed copy, and `config.cpp`, unchanged, named to `shakedown reload` together. Each file was level `game-restart`; the new file's reason: "A new or deleted file: file patching finds only files that exist in the built PBO, so the mod must be rebuilt before this reload, which restarts the game."; the config's: "Config is read at game start, so the game restarts." Every machine came back `ready` with its start number one higher.
- **US-055** A final function reloaded by a game restart: the staged `fnc_version.sqf` changed from `"1"` to `"2"`, then `shakedown reload --json` with no files: level `game-restart`, the staged file with the reason "The game holds every mod file it has read and reads a changed one only in a new process, so the game restarts. The mod's rebuild runs while no game process runs.", machines `server`, `p1`, `p2`, `hc1`, and `duration_s`. The rebuild had copied the file into the installed copy. The next check saw `"2"` from `skdfx_cba_fnc_version` on every machine and `p1` and `p2` alive, on foot and unhurt at the start, and its result file gave every machine its start number one higher.
- **NFR-PF-02**: the six successful game-restart reloads of changed or named files took 47.2 to 48.1 s by `duration_s`, the rebuild included, with a headless client beside the two clients; every reload result gave its time.
- **US-057** A reload that does not complete: the staged file put back to `"1"`, `shakedown reload --json`, and `p2`'s new process ended by its id about 19 s in. The reload exited 4 with state `failed`, `machines` empty and `reason` `{"step": "game-restart", "machine": "p2", "message": "p2 exited with code 1 before it was ready; it was launched"}`. `status`, by command and by tool, showed the session `broken` naming `p2` and the reload. `shakedown run` exited 4: "Session ... is broken (...), so it cannot run checks. Bring every machine back with `shakedown reload`, which restarts its game, or stop it with `shakedown session stop`."; `run_start` returned `session-broken`. The `reload` tool then answered `done` in about 47 s, level `game-restart`, every machine `ready` with a new start number, the rebuild having put `"1"` back, and the next check saw `"1"` on every machine.
