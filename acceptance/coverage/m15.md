# M15 Hand over to the manual tester: coverage

The M15 run: `python acceptance/run.py --repeat 3 --check US-083 --check US-084`, selecting the 14 M15 checks, from 15:39Z to 15:45Z on 2026-11-18. The framework was the install in `target\shakedown\` of the main checkout, built from the last M15 commit on main (`01b7fcd`); `shakedown version` prints `0.1.5`. Steam ran for every start, no start was lost to `Error 20 reading file`, and every client connected within the start ceiling. 42 of 42 passed, each check 3 of 3. Two trial rounds before it ran each check once; the first showed two mistakes of the checks, fixed before the run (below).

## How the checks drive it

The project `m15` of the harness, in the work folder, with the checks of `acceptance/m15/` and two setups, each loading `@skd_fixture` alone: `sp` (singleplayer) and `ded` (a dedicated server with two clients and a headless client), in that order. The crate check places `p1` at `[150, 150]`, creates `skdfx_Crate` 3 m in front of it and calls `skd_fnc_handOver` on `p1` with the three items of `docs/handing-over.md`; the US-084 checks place `p1` at `[200, 200]`, create a crate and hand over to `server` or `hc1`; a baseline check asserts that the server sees no `skdfx_Crate` and that `p1` stands more than 2 m from both places. Per repeat, with no session before each part:

- `ded`: `run --setup ded US-083-crate US-083-after` (US-083 1 to 3); in the session it left up, `status`, `exec` of `getPosASL player` on `p1` and of the crate count on `server`, and `logs --machine p1`; `run US-083-baseline` (the next run); `run_start` of the same two checks through `shakedown mcp`, `run_status` until it ended and `run_result`, validated against the outputSchema `tools/list` gives it; `exec` again, `reset`, `exec`; `run --json` of the two checks, then `reload` with nothing changed, `status` and the baseline check; `run US-084-server US-084-hc1 US-083-baseline` (US-084); one more hand over by `run`, then `session stop`, with each game process waited on by its id.
- `each`: `run --each-setup US-083-each US-083-after US-083-dedonly`, where `US-083-each` names `sp` and hands over there, `US-083-after` names both setups and `US-083-dedonly` names `ded`, while the game processes are listed every second; `status`, `exec` on `p1`, and `session stop`.

Every result file read was validated against `result.schema.json`, whose `HandedOver.items` carries `maxItems`; the harness's validator learned that keyword in this round.

## The stories

- **`US-083`**: `run --setup ded` exited 0 in 47 to 51 s, including the start. It printed `pass    US-083-crate  (2.0 s)` with `handed over to p1` on the line under it, the summary `1 passed, 0 failed, 0 invalid, 1 not run. Result: ...`, then `Handed over to p1 by US-083-crate. Look through p1's window for:`, the three items numbered 1 to 3 in order, and `Session s-... stays up for you. End it with `shakedown session stop`.` (1). The result file carried `handed_over` `{machine: p1, items: [the three]}` on the `pass` execution and listed `US-083-after` as not run with reason `handed-over`, and was valid; `run --json` and `run_result` gave `handed_over` with the check, repeat 1, `p1`, the items, the session's id and `shakedown session stop`, and `run_result` was valid against its outputSchema (1). After each hand over `exec` read `p1` within 1.5 m of `[150, 150]` and the server saw the crate, and `p1`'s RPT held the three items (2). `status` showed the session the command had started `ready`, on setup `ded`, with `server`, `p1`, `p2` and `hc1`, each process running, and the id the command printed (3). The next `run`, `reset` (state `done`, 0.5 s), `reload` (0.1 s, nothing changed) and `session stop` each took the session back: the baseline check passed after the run and after the reload, after `reset` the crate was gone and `p1` back at its start, and after `session stop` `status` showed no session and no game process of it ran (4). In `run --each-setup`, the hand over in `sp` kept that session up and `ready` with `p1` at `[150, 150]`, no dedicated server process started (one `arma3_x64` was seen), the command exited 0 and printed the hand over, and `sp`'s result file listed `US-083-after` as not run `handed-over`. 3 of 3.
- **`US-084`**: on the dedicated session with two clients and a headless client, the hand over to `server` ended `fail` / `check-error` with `skd_fnc_handOver: server has no screen a person can look through. Hand over to a game client: p1, p2.`, and the one to `hc1` the same with `hc1`; neither carried `handed_over`. The run went on: the baseline check after them passed, so the reset ran and put `p1` back from `[200, 200]` and removed the crates; the run exited 1 with no `handed_over` and nothing not run, and the session stayed `ready`. 3 of 3.

What the manual tester sees in `p1`'s window, the box titled `Shakedown: look for` at the top left, is the owner's look (exit criterion 3) and is not judged here; the checks read the output, the result file, `run_result`, `status`, positions through `exec` and `p1`'s RPT.

## Mistakes of the checks, fixed

- The first trial placed `p1` at `[100, 100]`, where the session mission's `p1` starts, so the checks that `p1` was back at its start after a reset could not tell; the hand over now places `p1` at `[150, 150]`.
- `docs/handing-over.md` says the check's line carries `handed over to p1`; the command prints it on the line under the check's line. The check accepts either; the docs' example shows the summary and the block, not that line, so this is not a finding.
