# M10 The grappling-hook suite: coverage

M10 has no stories of its own. It proves the stories of M0 to M9 together on arma-grappling-hook. Its checks are the exit criteria that belong to the tester (1, 2, 4, 5, 6 and 8), run over that mod's ported M00 checks, and the checks of its five findings. The `results` above list the stories those finding checks carry. The exit-criterion checks carry `M10 EC<n>` and the requirement IDs in their names.

The last run: `python acceptance/run.py`, the full suite of every milestone, once, from 17:18Z to 18:23Z on 2026-11-13. The framework was installed from the main checkout at `780496e`, and the harness was this round's work on top of it. No start was lost to `Error 20 reading file`. 300 checks ran and 298 passed, the 23 M10 checks among them. Every check of M0 to M9 passed.

Two checks failed, both on one execution of a ported check: `M10 EC5 CR-27 CR-53 AGT-01 ... reaches the outcomes the command line reached ...` and `M10 EC8 NFR-RL-01 NFR-RL-02 SPK-14 over the agent's ported runs ...`. In the agent's `sp-cba-ace` run, arma-grappling-hook's `US-064-1` ended `fail` / `assertion`, though the command line's run of the same repeat passed it. The cause is in the ported check and the mod under ACE, not in Shakedown:

- In the failed run, the let go 5.02 m up did no leg damage (`legs=0.000`), while ten of the game's own falls from the same point did 0.45 to 0.95. Five more `run --setup sp-cba-ace` runs from the command line after the full run failed it once more the other way round: the let go did 0.95, and the game's own falls did 0.45, 0.5 and once 0.000. ACE's leg damage from a 5 m fall is random, and the check's comparison does not always take it in.
- Over the round, the full run and those five runs, `US-064-1` with ACE ran 13 times and failed 2. Without ACE (`sp-cba`) it passed 8 of 8. In both failures the check ran to its end with no script error, no lost machine and no failed reset. The outcome was decided inside the check body by values the mod and the game produced.
- It is not a finding for this repository. The flaky check is arma-grappling-hook's, which the tester may run but not change, so it goes to that repository's roles. The two M10 checks report it as they should: the agent's outcome really did differ from the command line's in that repeat.

The `nosteam` and `claude` checks are not part of a run without `--check`.

### Exit criterion 5: the agent

The harness acts as the agent. It starts `shakedown mcp` from the copy's `.mcp.json` with the install folder on `PATH`, and speaks JSON-RPC to it. Per setup it calls `session_start`; for `dedicated-cba`, which takes longer than the 50 s the call waits, it follows with `status` until `ready`. Then `run_start` with the setup, `run_status` with `wait_s` 45 until the run ends, `run_result`, and `session_stop`. In every repeat the outcomes of each setup's run were the command line's, check by check, and `run_result` agreed with its result file.

The diagnosis: in the `sp-cba` session the agent writes `CTL-01-hold-diagnose`, `CTL-01-hold` with one assertion turned round to expect `p1` to climb up while climb down is held, and runs it. `run_result` gave `fail` / `assertion`, the failed step `climb down acts while held`, and "p1 climbs up 0.5 m while climb down is held (changed on purpose): expected > 21.89 on p1 within 5 s, last read 18.90". `inspect` of `p1` then gave the living player more than 0.5 m below the tower's top, which the check attached as `lip`. So the player went down as the key says, and the assertion is what is wrong. `logs` gave `p1`'s lines for the check. 3 of 3.

## Decisions of the test developer

- **The ported suite runs from a copy.** The tester may run arma-grappling-hook's project but not change it. The project has no `.mcp.json`, and the agent needs one to start the server, so the harness copies `checks/` and `shakedown.toml` into its work folder and adds one. The diagnosis check and the edit loop's edit live only in that copy. The edit is undone after its run, and the diagnosis file is deleted.
- **The ported checks must pass.** Exit criterion 7 says they reach the PowerShell verdicts on the same build, and that suite passed them, so any non-pass outcome fails `M10 EC4`.
- **`NFR-PF-01` on a dedicated session is measured with `CTL-01-keys`**, after `dedicated-cba` is added to its `@setups` by the edit. Both ported dedicated checks run longer than 10 s, and adding a setup is the kind of edit the requirement is about.
- **"Diagnoses with `inspect`"** is read as: the agent reads the failed step and the reason from `run_result`, then finds the game state that explains the failure with `inspect`, while the session is still up.
- **The m10-2 control** was added so that the m10-2 check cannot pass because the reset itself restores `allowDamage`.
