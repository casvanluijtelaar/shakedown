# M14 Reload without a game restart: coverage

The M14 run: `python acceptance/run.py --repeat 3 --check US-081 --check US-082`, selecting the 15 M14 checks, from 14:14Z to 14:34Z on 2026-11-18. The framework was the install in `target\shakedown\`, built from the last M14 commit on main; `shakedown version` prints `0.1.4`. Steam ran for every start, no start was lost to `Error 20 reading file`, and every client connected within the start ceiling. 45 of 45 passed, each check 3 of 3. A trial round before it, with ten reloads per session, passed every check once.

## How the checks drive it

Two sessions of the generated project, each loading CBA, `@skd_fixture` and `@skd_fixture_cba`, with `@skd_fixture_cba` watched in a staged copy of its sources in `stage\` and a `rebuild` that copies the staged `fnc_version.sqf` into the installed copy, as `spec/contract/fixture-mod.md` gives it (`FIX-03`): `m14`, a dedicated server with two clients, and `m14sp`, singleplayer. Per repeat, in each:

- `US-081`: four times (ten over a round of three would need `ceil(10 / 3)`), the staged file set to a value the session has not had (`"2"`, `"3"`, ...), `shakedown reload --json` with no files, and at once `shakedown run m14/US-081-version`, a check rewritten before each reload from `templates/US-081-version.sqf` to expect that value from `onEach` on every machine. `status --json` was read before and after each reload for each machine's process id and start number.
- `US-082`: `shakedown exec --machine server` (`p1` in singleplayer) of `["skdfx_cba\addons\main\functions\fnc_version.sqf"] call skdfx_fnc_holdFile` (`FIX-04`), then the staged file changed again, `shakedown reload --json` and the same check.

The staged and installed file were put back to `"1"` after each session stopped.

## The stories

- **`US-081`**: every one of the 24 reloads exited 0 with `state` `done`, `level` `mission-restart`, `machines` every machine of the session, and the staged file at level `mission-restart` with the reason "The game is made to let go of the file by reading the framework's release files, and a mission restart compiles it again. The mod's rebuild runs once no game process holds the file."; the rebuild had copied the new value into the installed copy. On the dedicated session the server kept its process id and start number and `p1` and `p2` came back `ready` one start higher; in singleplayer `p1` kept its process id and start number. The check after each reload passed, `skdfx_cba_fnc_version` giving the new value on `server`, `p1` and `p2`, 12 of 12 on the dedicated session and 12 of 12 in singleplayer, each execution with `reload` `full`, since a CBA `PREP` change has no machine recompile a `CfgFunctions` function (`DM-08`). `duration_s` was 49.6 to 51.0 s on the dedicated session (target 90 s plus the rebuild) and 7.99 to 8.22 s in singleplayer (target 20 s); in singleplayer the time from writing the staged file to the check's outcome was 9.7 to 10.3 s, under the 30 s of `NFR-PF-01` and criterion 3. `skd_release` in the game folder held `l00` to `l79`, each a junction to one folder holding a file of 8 MiB (`RLD-07`). 3 of 3.
- **`US-082`**: `skdfx_fnc_holdFile` answered `true`. The reload exited 0 with `level` `game-restart`, and the staged file's entry gave `game-restart` with the reason "C:\Program Files (x86)\Steam\steamapps\common\Arma 3\skdfx_cba\addons\main\functions\fnc_version.sqf is still held by server's process after two reads of the framework's release files: the game did not let go of it, so the game restarts." (`p1's process` in singleplayer). Every machine came back `ready` in a new process one start higher, and the check after it saw the new value on every machine. `duration_s` was 57.7 to 58.4 s on the dedicated session and 34.9 to 36.3 s in singleplayer. 3 of 3.

## The earlier checks M14 touched

M14 changed the level of a changed `.sqf` from `game-restart` to `mission-restart`, and `US-054`, `US-055` and `US-057` with it. These checks of M6 and M7 asserted the old promise and were brought up to the current contract; their names changed with them:

- `US-055 ... reports mission-restart, the file with the reasons that the game is made to let go of it, a mission restart compiles it and the rebuild runs, ...`: level `mission-restart` for the reload and the file, and the reason of `RLD-02`, instead of `game-restart` and "new process".
- `US-055 RST-02 NFR-RL-04 INT-CBA-02 ... the lead keeps its start number while every other machine has one higher`: `US-055` 2 as edited; before, every machine one higher.
- `NFR-PF-02 US-055 US-056 every game-restart and mission-restart reload of the round ...`: judges both levels against 90 s on the `rld` setup, as `NFR-PF-02` sets for a dedicated session with two clients.
- `US-057 ... p2 ended during a mission-restart reload of a changed .sqf ...`: the failed reload's `reason.step` is `mission-restart`, the level it was applying.
- `US-054 ... level mission-restart, the file with its reason ...` (both setups): level and reason of `RLD-02`.
- `US-054 RUN-01 RLD-05 DM-08 ... the lead keeps its start number while every other machine has one higher, ... each reload partial` (both setups): `US-054` 2 as edited, `partial` after a `CfgFunctions` function was recompiled.
- `US-054 NFR-PF-02 ...` and `NFR-PF-02 US-054 every mission-restart reload ...` (both setups): the `mission-restart` targets, 90 s on the dedicated session and 20 s in singleplayer.
- `US-054 FIX-03 the staged file put back to "1" and reloaded ...` (both setups): that reload is `mission-restart` too.

## Exit criteria

1. `US-081` and `US-082` pass their acceptance criteria on the test machine: held, as above.
2. `DEF-21`'s acceptance criteria: held as far as `US-081` and `US-082` state them; the owner's demo is the rest.
3. The spike's result in `research/` and the spec edited to it: the developer's; the checks work from the edited spec.
4. Every acceptance check carries the story or requirement ID it proves: held. The gates of `NFR-MT-03` and `docs/` are the developer's; the checks drove the framework as `docs/reloading.md` gives it.
5. The demo against arma-grappling-hook is the owner's and is not covered here; nothing in that checkout was run, edited or committed.

## Not driven

- The release files made by the first `mission-restart` reload on a game folder without them (`RLD-07`, `NFR-PF-02`'s one-off cost): `skd_release` was already in the game folder before the run, and removing it is no change `spec/contract/fixture-mod.md` allows a test.
- A file held by a client on the dedicated session: `US-082` names no machine; the checks hold it on the server, the machine a `mission-restart` reload keeps, and on `p1` in singleplayer.
- That the reload read the release files twice before falling back (`US-082` 1): not observable through the contract beyond the reason, which says so.
- A `config.cpp` among the changed `.sqf` files making the whole reload `game-restart`: the docs say it, no M14 story does.
- The read of the release files not answered by a machine: `US-057`'s failed reload covers a machine lost during a `mission-restart` reload.
